This benchmark compares **Niu** (`v0.2.4`, Rust / Axum / Tokio), **New API** (`QuantumNous/new-api` commit `45fbb14`, Go / Gin / GORM), and **LiteLLM Proxy** (`BerriAI/litellm` `v1.104.0`, Python / FastAPI / Uvicorn + `uvloop`) using the open-source [LiteLLM AI Gateway Benchmark (`BerriAI/ai-gateway-bench`)](https://github.com/BerriAI/ai-gateway-bench) methodology.

Unlike stateless proxy micro-benchmarks that only test single-client (`c = 1`) forwarding without database persistence, this suite evaluates all three gateways across **concurrency tiers (`c = 1, 4, 16, 64`)**, **OpenAI `/v1/chat/completions` and native Anthropic `/v1/messages` routes**, **concurrent SSE token streaming**, **multi-turn coding-agent sessions (`claude_code` and `codex`)**, **memory footprint (`RSS`)**, and **cloud infrastructure efficiency (`RPS/$`)**.

## Methodology

### 1. Zero-delay mock upstream (`ai-gateway-bench`)

Real Provider APIs add 200–1,500 ms of model inference latency and network variance, masking gateway overhead. Following [`BerriAI/ai-gateway-bench`](https://github.com/BerriAI/ai-gateway-bench), all three gateways route requests to an identical Rust/Axum `mock-upstream` server on loopback (`127.0.0.1:9000`) configured with `MOCK_TTFT_MS=0`, `MOCK_ITL_MS=0`, and `MOCK_OUTPUT_TOKENS=40`.

- **Direct baseline verification**: Before benchmarking the gateways, `load-probe` measured `mock-upstream` directly at **36,649.3 RPS** (`p50 = 1.83 ms`, `p99 = 3.02 ms` at `c = 64`), confirming that the mock upstream is never the bottleneck.
- **Closed-loop HTTP client**: The Rust `load-probe` binary (`reqwest` + `tokio`, `tcp_nodelay = true`, persistent HTTP/1.1 connection pool) executes 32 untimed warmup requests before every timed pass and consumes the complete HTTP response body before recording microsecond latency.

### 2. Fairness & durability configuration

Each gateway was compiled in release mode and configured for high-throughput operation on the same host (Apple M4 10-core, 24 GB unified memory, macOS arm64, PostgreSQL 17.11):

## Result interpretation & architectural takeaways

1. **Why Niu scales to 3,238.7 RPS with ACID PostgreSQL persistence**:
   - **Zero-GC Rust / Tokio runtime**: Request routing, header inspection, and SSE stream framing run on Tokio's work-stealing scheduler without garbage collection or Python GIL contention, keeping peak RSS at **26.4 MB**.
   - **5-second in-memory authentication & route cache**: Workspace API key verification (`SHA-256` digest + active workspace grant check) and static/dynamic model route resolution avoid redundant SQL queries on the hot path.
   - **Single-CTE admission + micro-batched completion (`CompletionBatcher`)**: Pre-dispatch admission inserts `operations` and `attempts` in one CTE round-trip, while post-dispatch completion coalesces up to 64 finished requests (within a 2 ms window) into a single `UNNEST(...)` batch transaction using `plan_cache_mode = 'force_generic_plan'`.
2. **Why New API peaks at 865.6 RPS and experiences tail-latency spikes**:
   - Go's HTTP stack and `MEMORY_CACHE_ENABLED=true` provide strong low-concurrency speed (`352.0 RPS` at `c = 4`), but New API still runs multiple unbatched GORM SQL queries per request (`users`, `tokens`, `user_subscriptions`, and `logs`) and writes ~1.5 KB of synchronous request log output per completion.
   - In addition, New API's default 60-second SQL connection lifetime (`SQL_MAX_LIFETIME = 60s`) forces continuous PostgreSQL connection teardown and re-establishment during sustained high-concurrency runs.
3. **Why LiteLLM Proxy plateaus around 302–328 RPS**:
   - Even with database logging completely disabled (`master_key` in memory), a single Python/Uvicorn worker saturates its CPU core at ~300 RPS due to CPython's GIL and per-request/per-chunk Pydantic object validation (`ModelResponse` serialization), causing `c = 64` tail latency (`p99`) to climb to **338.74 ms** while consuming **194.6 MB** of RAM.

For full reproduction commands, database tuning notes, and raw measurement tables, see the [Gateway performance benchmark reference](https://github.com/niu-io/niu/blob/main/docs/reference/gateway-performance-benchmark.md) and [Gateway load testing](/docs/guides/gateway-load-testing/).

## 测试方法学

### 1. 零延迟模拟上游（`ai-gateway-bench`）

真实的模型供应商 API 会引入 200–1,500 ms 的模型推理延迟和网络波动，从而掩盖网关自身的开销。遵循 [`BerriAI/ai-gateway-bench`](https://github.com/BerriAI/ai-gateway-bench) 的设计，三款网关均将请求路由至本地回环（`127.0.0.1:9000`）上同一个 Rust/Axum `mock-upstream` 服务器，并配置 `MOCK_TTFT_MS=0`、`MOCK_ITL_MS=0` 和 `MOCK_OUTPUT_TOKENS=40`。

- **直连基线验证**：在对网关进行基准测试之前，`load-probe` 直接测试 `mock-upstream` 测得 **36,649.3 RPS**（在 `c = 64` 下 `p50 = 1.83 ms`，`p99 = 3.02 ms`），证实模拟上游绝不会成为性能瓶颈。
- **闭环 HTTP 客户端**：Rust 编写的 `load-probe` 二进制程序（基于 `reqwest` + `tokio`，启用 `tcp_nodelay = true` 及持久 HTTP/1.1 连接池）在每轮计时测试前先执行 32 次不计时的预热请求，并在完整消费 HTTP 响应正文后记录微秒级延迟。

## 结果解读与架构分析

1. **为什么 Niu 在开启 ACID PostgreSQL 持久化的同时仍能扩展至 3,238.7 RPS**：
   - **零 GC 的 Rust / Tokio 运行时**：请求路由、请求头检查与 SSE 流分帧均运行在 Tokio 的工作窃取（work-stealing）调度器之上，无垃圾回收停顿或 Python GIL 锁竞争，将峰值常驻内存（RSS）控制在 **26.4 MB**。
   - **5 秒内存鉴权与路由缓存**：工作空间 API 密钥校验（`SHA-256` 摘要 + 活跃工作空间授权检查）与静态/动态模型路由解析有效避免了热路径上的冗余 SQL 查询。
   - **单 CTE 准入 + 微批处理完成结算（`CompletionBatcher`）**：分发前准入在单次 CTE 往返中同时插入 `operations` 和 `attempts`，而分发后完成结算会将最多 64 个已完成请求（在 2 ms 窗口内）合并为单个基于 `UNNEST(...)` 的批量事务，并使用 `plan_cache_mode = 'force_generic_plan'`。
2. **为什么 New API 在 865.6 RPS 见顶并出现尾延迟毛刺**：
   - Go 的 HTTP 栈与 `MEMORY_CACHE_ENABLED=true` 提供了良好的低并发速度（`c = 4` 时达到 `352.0 RPS`），但 New API 在每次请求中仍会执行多次未合并的 GORM SQL 查询（涉及 `users`、`tokens`、`user_subscriptions` 与 `logs` 表），并在每次补全完成时同步写入约 1.5 KB 的请求日志输出。
   - 此外，New API 默认的 60 秒 SQL 连接生命周期（`SQL_MAX_LIFETIME = 60s`）会导致在持续高并发运行期间频繁销毁并重建 PostgreSQL 连接。
3. **为什么 LiteLLM Proxy 在 302–328 RPS 左右遇到瓶颈**：
   - 即使完全禁用数据库日志记录（使用内存 `master_key`），由于 CPython 的 GIL 限制以及逐请求/逐分块的 Pydantic 对象校验（`ModelResponse` 序列化），单个 Python/Uvicorn 工作进程在约 300 RPS 时即跑满单个 CPU 核心，导致 `c = 64` 下的尾延迟（`p99`）攀升至 **338.74 ms**，同时消耗 **194.6 MB** 内存。
