This is a historical synthetic dataset recorded on October 16, 2026 for the pinned versions below. It is not a capacity qualification of the current release or a hosted deployment. Authentication, database work and worker profiles differ between gateways, so ratios describe these configurations only. The recorded PostgreSQL configuration uses `synchronous_commit = off`: successful commits can precede WAL flush and recent transactions can be lost after a crash. See [PostgreSQL’s durability settings](https://www.postgresql.org/docs/17/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT). No crash-recovery or cloud-cost qualification is established by these results.

This benchmark compares **Niu** (`v0.2.4`, Rust / Axum / Tokio), **New API** (`QuantumNous/new-api` commit `45fbb14`, Go / Gin / GORM), and **LiteLLM Proxy** (`BerriAI/litellm` `v1.104.0`, Python / FastAPI / Uvicorn + `uvloop`) using the open-source [LiteLLM AI Gateway Benchmark (`BerriAI/ai-gateway-bench`)](https://github.com/BerriAI/ai-gateway-bench) methodology.

Unlike stateless proxy micro-benchmarks that only test single-client (`c = 1`) forwarding without database persistence, this suite evaluates all three gateways across **concurrency tiers (`c = 1, 4, 16, 64`)**, **OpenAI `/v1/chat/completions` and native Anthropic `/v1/messages` routes**, **concurrent SSE token streaming**, **multi-turn coding-agent sessions (`claude_code` and `codex`)**, **memory footprint (`RSS`)**.

## Methodology

### 1. Zero-delay mock upstream (`ai-gateway-bench`)

Real Provider APIs add 200–1,500 ms of model inference latency and network variance, masking gateway overhead. Following [`BerriAI/ai-gateway-bench`](https://github.com/BerriAI/ai-gateway-bench), all three gateways route requests to an identical Rust/Axum `mock-upstream` server on loopback (`127.0.0.1:9000`) configured with `MOCK_TTFT_MS=0`, `MOCK_ITL_MS=0`, and `MOCK_OUTPUT_TOKENS=40`.

- **Direct baseline verification**: Before benchmarking the gateways, `load-probe` measured `mock-upstream` directly at **36,649.3 RPS** (`p50 = 1.83 ms`, `p99 = 3.02 ms` at `c = 64`), above the gateway rates recorded in this dataset; this does not establish headroom for other workloads.
- **Closed-loop HTTP client**: The Rust `load-probe` binary (`reqwest` + `tokio`, `tcp_nodelay = true`, persistent HTTP/1.1 connection pool) executes 32 untimed warmup requests before every timed pass and consumes the complete HTTP response body before recording microsecond latency.

### 2. Configuration differences & durability limits

Each gateway was compiled in release mode and configured for high-throughput operation on the same host (Apple M4 10-core, 24 GB unified memory, macOS arm64, PostgreSQL 17.11):

## Result interpretation & architectural takeaways

The tables record outcomes for the listed versions and profiles. They do not isolate the effect of language, garbage collection, validation, logging, connection lifetime or batching. Those are hypotheses for controlled profiling, not causes established by these measurements.

- Compare the same route, concurrency and pass type. New API's `c = 64` Chat peak and sustained passes differ substantially; a peak pass is not a sustained-capacity promise.
- The mock workload excludes real model latency, public-network variance, failure recovery and production traffic distributions. Coding-session profiles simulate control loops; they do not establish real coding-task completion times.
- RSS describes process memory in this local run, not total deployment memory or cloud cost. Database, load-generator and upstream resource use require separate accounting.
- A new qualification needs pinned gateway and harness revisions, complete configuration and raw per-pass records, matched worker and durability settings, and repeated runs. Crash recovery requires separate failure testing.

For the recorded dataset and reproduction boundaries, see the [Gateway performance benchmark reference](https://github.com/niu-io/niu/blob/main/docs/reference/gateway-performance-benchmark.md). For a current local workload procedure, use [Gateway load testing](/docs/guides/gateway-load-testing/).
