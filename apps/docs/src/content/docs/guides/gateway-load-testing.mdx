## Reproduce a gateway load run

The repository includes a dependency-free HTTP load client for OpenAI-compatible
chat completions. It supports fixed concurrency and scheduled request-rate
profiles, reuses one connection per worker, excludes warm-up calls, and writes
latency percentiles, HTTP status counts, throughput, scheduled-start lag, and
transport errors to JSON. An optional bearer key is read from an environment
variable and is never copied to the report.

```sh
python3 scripts/gateway-benchmark.py \
  http://localhost:2555/v1/chat/completions \
  --model fast \
  --bearer-env NIU_BENCHMARK_TOKEN \
  --mode concurrency --workers 64 --duration 30 \
  --out gateway-run.json
```

To use a fixed arrival rate, pass `--mode rate --rate 500 --workers 64` instead.
Rate runs count starts that exceed `--max-start-lag-ms` as dropped and return a
nonzero exit status for drops or failed responses. Repeat each configuration at
least five times, use the same machine and actual configured upstream, rotate run order,
and retain every JSON report. Measure CPU and resident memory separately for the
gateway and PostgreSQL; record the database version, pool size, schema revision,
gateway commit, deployment mode, host resources, and upstream model/adapter. After a
run, reconcile accepted requests, attempts, usage, reservations, and settlements
from the gateway's persisted records. HTTP 200 alone does not establish valid
model output or complete streaming delivery. Independently inspect current-input
outputs, terminal events and usage, then compute expected charges from the pinned
customer tariff and compare each charge, debit and released reservation. Preserve
all failed or uncertain attempts; never silently retry them out of a report.

The client measures end-to-end HTTP time, including upstream and response-body
time. Warm-up calls are excluded from the report but still execute and may be
billable against a live provider. Set an explicit request/spend bound before
using an authorized upstream. Fixture results provide no evidence of correctness,
performance qualification, or readiness. The client does not report isolated proxy
overhead, time to first token, PostgreSQL resource use, or model quality. Keep
unpriced traffic separate from priced
admission and settlement runs, since those paths exercise different storage
work. Do not treat a chat-throughput result as an accepted-task economics
benchmark.

Vendor benchmark claims are methodology references, not independent evidence
or an apples-to-apples Niu comparison. LiteLLM's published page describes a
single-client run against a deterministic mock upstream. Bifrost's open
[benchmark tooling](https://github.com/maximhq/bifrost-benchmarking) provides
Vegeta-based fixed-rate and fixed-user runs, a mock provider, latency and
throughput reports, and optional gateway RSS sampling. Pin the releases and
match the protocol, payload, routing and authentication work, upstream conditions, load
profile, hardware, and measurement definitions before comparing results. Keep
measured gateway-added latency separate from end-to-end request latency.
References: [LiteLLM's published benchmark](https://www.litellm.ai/ai-gateway)
and [Bifrost's benchmark repository](https://github.com/maximhq/bifrost-benchmarking).

## Current native structured-stream checkpoint

A 60-second admission window with four workers produced 71 independently
verified structured streams in 63.630 seconds including drain. Each returned its
fresh marker and complete requested integer sequence. Independent usage-based
arithmetic matched every customer charge and debit, no balance hold remained,
and restart preserved the same records. Completion P50/P95 was 3.262/4.947 seconds,
including real upstream generation. This single run does not establish production
capacity. The [detailed workload and boundaries](https://github.com/niu-io/niu/blob/main/docs/reference/structured-output-streaming.md#one-minute-structured-stream-load-checkpoint)
include rates, process samples and accounting checks.

A subsequent run with immutable operation tariff bindings completed 70 verified
streams in 63.256 seconds, with completion P50/P95 of 3.418/4.319 seconds. All
70 operation/attempt price bindings agreed; each charge matched reported usage,
all holds were released and restart preserved the debit count. This includes
upstream generation and is not an isolated measurement of binding overhead or
maximum capacity. See the [operation-tariff checkpoint](https://github.com/niu-io/niu/blob/main/docs/reference/structured-output-streaming.md#operation-tariff-concurrency-checkpoint).


## Concurrent bounded Chat failover checkpoint

A four-worker run with a 60-second admission window completed 54 structured
streams in 63.821 seconds including drain. Every operation first received a real
OpenRouter authentication rejection, then completed on another credential:
108 durable attempts, 54 exact customer charges/debits, no remaining holds and
unchanged chains after restart. Saved outputs and independently reopened database
records were checked separately. Completion P50/P95 was 4.531/5.272 seconds,
including rejection, selection and upstream generation; completed-operation
throughput was 0.846/second.

This checks the exercised concurrent workflow rather than maximum capacity or
isolated retry overhead. It is not a controlled comparison with the earlier
single-attempt runs. See the
[workload, accounting evidence and measurement limits](https://github.com/niu-io/niu/blob/main/docs/reference/upstream-retry-policy.md#concurrent-bounded-failover-checkpoint).

## Two gateways sharing PostgreSQL

A subsequent current-input run split four workers between two native gateways,
with eight database connections per instance. During a 60-second admission window,
53 actual streamed operations completed in 64.194 seconds including drain.
Completion P50/P95 was 4.593/5.657 seconds, including the real authentication
rejection and subsequent upstream generation.

Independent inspection parsed every saved raw SSE response and reopened the
retained database: 106 attempts, 53 exact charges/debits, no remaining holds,
and unchanged chains after restarting both gateways. This verifies distinct
concurrent operations across instances; it does not establish maximum capacity,
competing successors for one operation or restart during active generation.
See the [two-gateway evidence and limits](https://github.com/niu-io/niu/blob/main/docs/reference/upstream-retry-policy.md#two-gateway-shared-database-checkpoint).

## Crash safety during a real stream

A separate actual request run killed the isolated gateway with SIGKILL after the
first streamed content event. Restart retained unknown usage, a pending charge
and its balance reservation. There was no automatic failover or invented debit;
the key's exhausted spending allowance still rejected new dispatch after rotation
and restart. Independent raw-response and database inspection confirmed the final
state. This is a crash-boundary check, not a throughput measurement or proof that
unknown upstream usage can later be recovered. See the
[hard-crash evidence and limits](https://github.com/niu-io/niu/blob/main/docs/reference/upstream-retry-policy.md#hard-process-crash-after-streamed-output).

## A gateway joining during generation

A second native gateway was started after the first instance had delivered actual
stream content. SQL before and after the new instance became ready showed the
original request still executing with unknown usage and its reservation held.
Both instances then served traffic: 18 completed operations, 36 attempts and 18
exact charges, with no remaining holds or duplicate charges after restart.
Independent raw-response and reopened-database checks confirmed the results.
This checks peer startup during live work, not a full zero-downtime rolling
replacement. See the [startup evidence and remaining boundaries](https://github.com/niu-io/niu/blob/main/docs/reference/upstream-retry-policy.md#joining-a-gateway-during-active-generation).

## Graceful drain of an active stream

A current native run sent SIGTERM after the first actual stream content. The
client still received terminal output and provider usage; the process exited zero
after persisting a single exact charge/debit and complete request timing. All
holds were released. Independent raw-SSE and reopened-database inspection agreed,
and restart created no duplicate request or charge. This qualifies the exercised
graceful drain, not stalled upstreams, forced drain deadlines or a complete rolling
deployment. See the [signal and accounting evidence](https://github.com/niu-io/niu/blob/main/docs/reference/upstream-retry-policy.md#graceful-termination-during-actual-streaming).
