Read the [implemented API operations](/docs/reference/handler-operations/) for
handler-generated parameters, request bodies, response schemas and error states.
This reference currently covers an annotated subset; other interfaces remain in
the root OpenAPI contract below.

The versioned OpenAPI contract is maintained in [`contracts/openapi.yaml`](https://github.com/niu-io/niu/blob/main/contracts/openapi.yaml). It describes the implemented inference routes and scoped management workflows. The management surface is still partial; the first-release matrix tracks remaining route editing, audit coverage, policy, and reconciliation work.


The public API surface must preserve protocol-specific behavior. Unsupported parameters and event types are rejected or passed through according to the operation contract; they are not silently discarded.

Inference routes accept either `Authorization: Bearer <workspace-key>` or
`X-Niu-API-Key: <workspace-key>`. Use the latter when a client must keep a
provider credential in `Authorization`; the Niu key remains scoped to its
workspace and is consumed at the gateway. This header only separates
the two credentials. Provider-specific auth forwarding and subscription
eligibility still depend on the configured route and supported client protocol.

## Frontend integration contract

Use the [implemented API operations](/docs/reference/handler-operations/) to inspect
method, path, authorization, request fields, response schemas and documented
errors. Download the [generated OpenAPI JSON](/docs/openapi/handler-operations.json)
for that annotated subset. Use the root contract above for additional interfaces;
the generated subset is not the complete backend surface.

Keep HTTP errors distinct from successful empty results. A declared unsupported
operation must retain its documented error instead of returning fabricated data
or a successful mutation. Revision conflicts require re-reading current state.
Preserve the original idempotency identity when recovering an uncertain submission.
A streaming HTTP 200 is not proof of successful generation: consume the stream's
terminal state and handle its error event.

## Chat drafts

`GET` and `PUT /admin/v1/organizations/{organization}/projects/{project}/chat-draft`
read and save the authenticated actor's unsent composer state in PostgreSQL.
This is separate from sent conversation history. Reads require workspace read
access; writes require workspace write access. Responses use `Cache-Control:
no-store` and return `{data: {payload, revision}}`. A missing draft has a null
payload and revision zero.

PUT accepts `expected_revision` and `payload`. The payload contains `sessionId`
(null for a new chat), `prompt`, `models`, `attachments`, and `settings` with
`systemPrompt`, `maxTokens`, `temperature`, and `logPayloads`. Up to four unique
models and four attachments are supported. Text fields are bounded to 12,000
characters; each attachment contains `name`, `type` (`image` or `text`), and
`content`. Unknown fields, including credential fields, are rejected. A referenced
conversation must belong to the same actor and workspace. The request body is
limited to 24 MiB. Browser writes require the configured same origin.

Saving requires the last read revision. A stale revision returns HTTP 409 without
replacing the draft. Set `payload` to null to clear it; clearing increments the
revision so another tab's old write cannot recreate the discarded draft. This
endpoint does not detect secrets deliberately included in prompt or file content.

## Customer billing

The [customer billing contract](https://github.com/niu-io/niu/blob/main/contracts/billing.openapi.yaml), included by the main OpenAPI document, covers workspace-authorized billing summaries and invoice line reads. Customer charges use explicit selling tariffs, independent from Supplier prices. Unpriced requests are not assumed free; unresolved charges remain unknown. Monetary amounts and aggregate counts are exact decimal integer strings. Workspace billing tariff lists and model-discovery customer prices include every matching saved tariff; they do not silently stop at 1,000 entries. These compatibility responses remain unpaginated, with memory use proportional to their size.

Tariff publication, invoice creation and confirmed external-payment recording require installation authority. Invoice intervals use UTC dispatch timestamps with an inclusive `from_ms` and exclusive `to_ms`, bounded to 366 days. Preserve the caller's idempotency key when replaying the same invoice request. Overlapping periods, unresolved priced requests and changed replay parameters produce conflicts; clients must not retry these by inventing a new key.

The JavaScript SDK provides `getCustomerBilling`, `publishCustomerTariff`, `issueCustomerInvoice`, `getCustomerInvoiceLines`, and `recordCustomerInvoicePayment`. Its packaged `inspect-billing.mjs` example reads the latest 100 invoices and reconciles line totals using exact integer arithmetic. Invoice creation does not send an invoice or collect money, and payment recording only records an already confirmed external payment. Keep administration credentials server-side and internal invoice/rate identifiers out of product displays.

### Company credit exhaustion and recovery

Already incurred text charges retain their full reported amount even if they
exceed the original reservation or approved company credit. Balance and available
capacity can therefore be negative. New paid requests require sufficient available
capacity and can return HTTP 402 `budget_exceeded`; billing reads remain available.
A balance refund is a separate ledger entry and does not erase the original charge.
The charge-reconciliation API compares gross original charges with their original
balance debits; it does not subtract refunds. Use the balance ledger for net funds.
[Actual nonempty reconciliation and refund verification](https://github.com/niu-io/niu/blob/main/docs/reference/customer-charge-reconciliation.md#nonempty-charges-and-partial-refund--2026-10-10)
records the current text-accounting boundary.
Preserve the refund idempotency key when replaying the same administrative action.

An actual credit-backed run verified overrun settlement, refusal across restart,
an idempotent internal refund and a subsequent real model completion. This does
not establish bank refund or customer-funded video behavior. See the
[actual company-credit evidence](https://github.com/niu-io/niu/blob/main/docs/reference/internal-credit-workflow-live.md#actual-company-credit-overrun-and-refund-recovery--2026-10-10).

### Personal calls and procurement limits

An authorized personal upstream route is funded by its credential owner. It does
not reserve or debit Niu customer funds or platform procurement budgets. A saved
workspace procurement budget therefore does not by itself prevent an authorized
personal Chat or video call. Current key/model permissions, Guardrails and request-rate
controls still apply. Shared priced routes retain procurement admission checks;
this distinction does not grant access to another company's personal credential.
Personal and customer-priced operations retain an immutable funding source across their attempt bindings; candidate selection cannot switch between them. Chat pools support one bounded successor after a qualified immediate OpenRouter authentication rejection; uncertain execution is never retried.
Personal text requests prepare their operation, route and admission bindings atomically before the separate dispatch permission check. A failed preparation does not leave a partially bound request. This does not enable automatic retries after uncertain dispatch.

Shared video routes retain the legacy procurement-budget restriction; personal video routes do not reserve or debit that budget. Personal video still enforces key RPM/concurrency controls. A finite key token-rate budget rejects video with `422 key_token_bound_required` when the channel lacks a supported token admission bound.

## API key spending allowance

Key spending limits apply to new customer-liability reservations. Read
`committed_nanos` and `remaining_nanos` from the spending-limit API; preserve these
exact decimal integer strings rather than converting them to floating-point money.
Remaining allowance is clamped to zero when actual consumption exceeds the cap.
A cap does not truncate an already incurred charge or cancel upstream work.
Secret rotation retains the same spending identity and committed amount.

An actual streamed text request exceeded its requested output bound: the original
1,000-nano reservation was released, the full 11,000-nano customer charge was
posted, and the rotated key showed zero remaining allowance and rejected further
requests before and after restart. This is a scoped text-accounting observation,
not qualification of media overruns or every provider. See the
[verification details](https://github.com/niu-io/niu/blob/main/docs/reference/api-key-spending-limits.md#actual-text-overrun-rotation-and-restart--2026-10-10).

## Route pool updates during generation

Platform administrators can discover saved pools through
`GET /admin/v1/model-route-pools/index`, or the SDK's `listModelRoutePools` method.
Pass `limit` (1–100, default 50), then use the returned `next_after` as `after` for
the next page. The list includes enabled and disabled configurations. Its live
alias-based traversal is not a snapshot; refresh from the first page to see
new aliases inserted before the current cursor. Existing alias lookup and
revision-history endpoints retain their response formats.

Inference model discovery traverses all saved route-pool pages rather than silently
limiting discovery to the first 1,000 pools. Disabled and unauthorized pools remain
excluded. The compatibility `/v1/models` response remains a complete list; bounded
database fetches do not imply a fixed-size response or a cross-page snapshot.
Workspace discovery applies shared and eligible personal pools once per request; it does
not resolve the shared inventory again after adding personal mappings.
Personal ownership is read with internal route metadata, avoiding a separate
ownership query for every mapping; it does not add fields to customer responses.

A revisioned pool update applies to selection for new requests. Disabling a
candidate does not cancel a generation already dispatched through it. That request
retains its original mapping and pool revision for diagnosis and accounting;
subsequent requests can select another eligible candidate under the new revision.
Customer model aliases and customer tariffs remain separate from Supplier mappings.

This behavior has been exercised with actual concurrent priced requests and
independent charge/revision checks. Separately, Chat pools can try a different
credential after a canonical OpenRouter immediate HTTP 401, once durable
nonexecution and released reservations are confirmed. The limit is two submitted
attempts under one operation and deadline, preserving customer price and funding
source. Other errors and streams already returned to the client are not retried. See the
[route pool contract and evidence](https://github.com/niu-io/niu/blob/main/docs/reference/model-route-pools.md).

## Customer request diagnostics

The workspace request list and detail endpoints report the customer model alias,
execution state, reported usage, customer charge and saved timing. A pool's selected
Supplier mapping and confidential procurement prices are not customer billing data.
Installation credentials receive the same customer-facing detail shape; they do
not expand it with wholesale costs. Request metadata responses use
`Cache-Control: no-store`.

Use the detailed response's nullable fields as documented in the
[generated request contracts](/docs/reference/handler-operations/). Missing timing
or usage is unknown, not a measured zero. Workspace scope applies to each request;
a foreign request returns 404. Display meaningful model/key names and timestamps
rather than the internal identifiers needed for API routing.

## Public model catalog

`GET /catalog/v1/models` and the `/models/` page list aliases an operator explicitly marks with `public_catalog = true`. The response contains the alias, declared capabilities, and optional descriptive catalog metadata such as name, context limits and modalities; it omits provider names, upstream identifiers, endpoints, credentials and Provider prices. Catalog visibility does not authorize inference. Applications still use scoped keys with `/v1/models` and the inference endpoints.

## Operator roles and sessions

The `operator` name is an existing administration API contract for a workspace
member; the dashboard uses **Users**. Accounts sign in with their own credentials
and receive their assigned role and workspace access. Installation setup
credentials are separate from member sessions and application API keys.
The password session API is opt-in through `NIU_AUTH_PUBLIC_ORIGIN`, which must
be an HTTPS origin without a path, credentials, query or fragment. Deploy it
behind HTTPS at that origin. Self-registration and
identity federation remain unimplemented.

`PUT /admin/v1/operators/{operator}/password` lets an installation administrator
or a scoped owner provision an existing member with `email`, `password` and
optional `expected_revision`. First provision omits the revision; resets require
the last returned revision and revoke all prior sessions atomically. Passwords
require at least 15 characters and at most 1,024 UTF-8 bytes; spaces and Unicode
are preserved. The response contains the new revision, never the hash.

`POST /admin/v1/auth/login` accepts `email` and `password` and returns a scoped
eight-hour bearer `token` and session metadata. It grants the member's existing
role and workspace access, never installation access. Wrong passwords and
unknown identities return the same HTTP 401 response. Durable admission limits
allow five attempts per normalized email and 120 per installation in a 60-second
window; limited requests return HTTP 429 with `Retry-After: 60`. Both routes
limit JSON bodies to 4 KiB and mark success/error responses `Cache-Control:
no-store`. A supplied browser Origin must match the configured origin. These
routes do not set browser cookies; the dashboard uses the separate browser
endpoints below. Without configuration, password login returns HTTP 501.
For same-origin browser clients, `POST /admin/v1/auth/browser/login` uses the
same credentials and limits, requires the configured HTTPS Origin and sets an
eight-hour Secure, HttpOnly, SameSite=Lax host-only cookie. Its JSON contains
session metadata without the bearer token. Shared member authorization validates
the saved session on every request and requires a matching Origin or browser
`Sec-Fetch-Site: same-origin` metadata; a mismatched Origin always fails.
Duplicate Authorization headers are rejected. When supplied, Fetch Metadata
must contain exactly one `same-origin` value even with a matching Origin.
Installation tokens are never accepted through this cookie path.
`POST /admin/v1/auth/browser/logout` requires the matching Origin, revokes the
current session and expires the cookie. Already unusable sessions still clear
successfully; storage failures do not claim sign-out or clear the cookie.
The dashboard discovers this mode through `GET /admin/v1/auth/config`, signs in
with the browser endpoint, and restores the server session without saving a
bearer token in browser storage. Real HTTPS browser acceptance remains unfinished.

`PUT /admin/v1/auth/password` lets every signed-in member role change its own
password with `current_password` and `password`. It accepts no member target or
email; installation credentials cannot use it. Current-password checks share
sign-in throttling, new passwords follow the same creation policy, and a
credential revision change during verification returns HTTP 409 without
replacing the newer credential. Success revokes all sessions for that member and
returns `sign_in_required: true`; other members remain unaffected. Browser-cookie
requests require the matching Origin and expire the cookie on success. Failed
changes preserve sessions. The dashboard provides password changes in account
settings; rendered review and HTTPS browser qualification remain open.

`GET /admin/v1/auth/preferences` reads the signed-in member's saved color mode.
`PUT /admin/v1/auth/preferences` accepts `{"color_mode":"system"}`, `"light"`,
or `"dark"` as the value of `color_mode`. Every member role can change its own
preference; installation tokens and caller-supplied member targets are rejected.
The default is `system`. Preferences are stored in PostgreSQL separately from
profile revisions, and browser storage is only a disposable cache. Dashboard and
embedded docs controls share this saved preference. Browser-cookie writes use
the same Origin checks as profile changes; responses are non-cacheable and
request bodies are limited to 1 KiB. Installation-only display choices have no
personal account to save to and remain local.

`POST /admin/v1/auth/logout` revokes the member bearer session in the
Authorization header. Every member role can sign out; other sessions remain
active. Revocation and its audit record are atomic, responses are non-cacheable,
and missing, expired or previously revoked credentials return HTTP 401.
Installation setup tokens are not member sessions. This API is available even
when password login is not configured. The dashboard uses the browser sign-out
endpoint for cookie sessions and preserves its session when revocation fails.

The [password session contract](https://github.com/niu-io/niu/blob/main/contracts/password-sessions.openapi.yaml)
documents request fields, role restrictions, session responses and failure statuses.

`NIU_ADMIN_TOKENS` remains the owner-level installation bootstrap credential. An owner can create persistent operators with `owner`, `admin`, or `viewer` roles through `POST /admin/v1/operators`, and issue additional expiring sessions through `POST /admin/v1/operators/{operator}/sessions`. Creation responses contain the bearer token once and include `Cache-Control: no-store`; list APIs return only identity, role, session IDs, expiry and revocation metadata. Delete an individual session or an operator to revoke access. A revoked or expired token fails the next administrative request.

Operator and session creation/revocation also append immutable, metadata-only audit events in the same database transaction. Events record whether the actor was an installation bootstrap credential or a scoped operator, the actor operator ID when present, target operator/session IDs, tenant scope and timestamp. They never store bearer tokens, token hashes or request bodies. A scoped owner can page through one operator's events with `GET /admin/v1/operators/{operator}/events`; pages are ordered by timestamp and event ID, limited to 1–100 items, and use `next_cursor` for stable continuation.

Owners can manage members. Admins can read and write management resources but cannot manage members. Viewers have read access only. Every member has an `organization_id` and may have a legacy `project_id` that restricts access to a single workspace. Owners cannot create or manage members outside their own scope. Workspace IDs in dashboard URLs do not grant authority. `GET /admin/v1/session` returns the caller's current identity, scope, and role permissions without exposing credentials.

The dashboard's `GET /admin/v1/workspaces` lists workspaces visible to the current administrator, with each workspace's parent organization. `POST /admin/v1/workspaces` creates one in the requested organization. Organization administrators can create workspaces only inside their organization; installation administrators can select any organization. If an installation has no organization yet, omitting `organization_id` creates a `Personal workspace` organization first. API keys, requests, budgets, and usage belong to a workspace; `project` names remain only in legacy API and storage contracts.

## Provider capability matrix

Capabilities are route-specific. Flags in `config/niu.toml` declare operator-verified behavior; they do not mean Niu has qualified every provider model or endpoint. A request for an unsupported combination is rejected before an attempt is created where the contract below marks it unavailable.

| Operation | OpenAI-compatible route (`provider = "openai"` or `"openrouter"`) | Native Anthropic route | Native Bedrock route |
| --- | --- | --- | --- |
| Chat completion, non-streaming | Supported; tool and structured-output subsets require separate route flags | Basic non-streaming adapter path | Basic non-streaming adapter path |
| Chat completion, streaming | Supported; tool deltas need `supports_streaming_tool_calls` | Not implemented | Not implemented |
| Function tools | Non-streaming tool-call pass-through with `supports_tool_calls`; Niu does not execute tools | Not implemented | Not implemented |
| Structured JSON output | Buffered and streaming `json_object` / `json_schema` with `supports_structured_output`; streaming deltas remain provisional until terminal validation | Not implemented | Not implemented |
| Text embeddings | Supported only with `supports_embeddings`; dimensions and base64 output require their own flags | Not implemented | Not implemented |
| Responses | Buffered and streamed text subset with `supports_responses` | Not implemented | Not implemented |

The native Anthropic and Bedrock entries describe the current non-streaming chat adapter path, not provider conformance qualification. Tool and structured-output capabilities are deliberately restricted to OpenAI-compatible routes. Pricing applies to bounded text chat, Responses and embeddings; embeddings reserve input capacity only and settle provider-reported prompt usage. Priced Chat supports the documented text-only function-tool conversations; Niu does not execute tools or price hosted tool services. See [Model routes](/docs/configuration/models/) for the exact route flags and pricing limits.

Non-streaming provider JSON responses are limited to 16 MiB before decoding. Larger responses fail as an upstream error and remain uncompleted in request activity. Streaming Chat inspects at most 65,536 bytes per Server-Sent Event; interrupted or cancelled streams remain uncertain unless a valid terminal event was observed.

## Chat function tools and structured output

Chat validates common generation parameters before admission or Supplier dispatch: `temperature` from 0 to 2, `top_p` from 0 to 1, and presence/frequency penalties from -2 to 2. Non-null `max_tokens`, `max_completion_tokens` and `n` must be positive signed 64-bit integers; non-null `seed` must be a signed 64-bit integer. Only one non-null output token limit may be supplied. `stream` must be boolean; non-null `stream_options` must be an object and its `include_usage`, when present, must be boolean. Invalid values return clear `400` errors without an operation or attempt. Omitted and nullable optional values preserve their existing semantics; Niu does not inject sampling defaults or clamp explicit values. A configured native adapter or priced route may impose stricter supported bounds.

`POST /v1/chat/completions` accepts OpenAI-compatible function tool definitions, `tool_choice`, and `response_format` values `json_object` or `json_schema` only when the configured OpenAI-compatible route explicitly enables the corresponding capability. Streaming tool-call deltas require the separate `supports_streaming_tool_calls` flag. Requests for disabled capabilities return `501` before an operation or attempt is recorded. The `unsupported_operation_error` message identifies tools, streaming tools or structured JSON and gives a supported alternative. Combined tools plus structured JSON remains unsupported; Niu does not silently remove those requested features. Malformed tool definitions, choices, and schemas receive `400`.

Niu forwards tool definitions and structured-output schemas to the provider. It does not execute tools. Non-streaming tool-call responses must reference a declared function and contain JSON-object arguments. Structured-output responses must match the self-contained JSON Schema; `json_object` responses must be objects. Schema compilation cannot retrieve HTTP or file references and has the [documented complexity limits](/docs/configuration/models/). Provider support must be independently verified by the installation administrator. These features are not enabled on native Anthropic or Bedrock routes. Token-priced routes support text-only function conversations. Structured JSON streams deliver provisional deltas and validate their assembled content before releasing `[DONE]`; invalid terminal content emits an `upstream_invalid_response` SSE error without `[DONE]` and records a failure while reported terminal usage remains accounting evidence. Validation retains at most 1 MiB of content/refusal bytes across 128 choices. A nonempty explicit refusal remains a refusal. Full Responses compatibility, broader protocol conformance, and provider-specific qualification remain release work. See the [structured-stream contract and current-input verification](https://github.com/niu-io/niu/blob/main/docs/reference/structured-output-streaming.md) for terminal error semantics, accounting and qualification limits.

If a terminal model response fails output validation, Niu returns `502` without delivering the rejected content. Valid, complete and consistent reported input/output token counts still record upstream completion and accrue the pinned customer charge; a failed delivery can therefore have a charge. Missing, invalid, inconsistent or overflowing usage remains unknown and is not replaced with an estimate. HTTP delivery status and upstream execution evidence describe different facts.

## Text request envelope limits

Public Chat, Responses, Embeddings and dashboard Chat reject request bodies over
1 MiB (1,048,576 bytes) with HTTP 413 before inference. The same limit applies
with or without payload retention, including chunked transfer without a
Content-Length header. A request at the byte limit still needs valid JSON,
supported fields, authorization and model-specific input bounds. Framework
rejections may use plain text rather than the API JSON error envelope.

## Responses API text subset

`POST /v1/responses` accepts a non-empty string `input` and optional string `instructions`, `max_output_tokens`, `temperature`, `top_p`, string-valued `metadata`, and `user`. The model route must set `supports_responses = true`; Niu rewrites the model to the configured upstream name and maps the returned model back to the public alias. The supported output subset includes text messages, reasoning items and refusal content in buffered or streamed responses. Usage maps from Responses `input_tokens`/`output_tokens` into durable prompt/completion fields.

Input arrays, images, audio, tools and conversation state are outside this subset. Unsupported fields or malformed shapes return `400`; a disabled route capability returns `501` before creating an attempt. Streamed completion requires terminal event and usage evidence; an initial HTTP 200 is not completion. When route pricing is enabled, `input` plus `instructions` must fit the configured conservative UTF-8 byte bound and `max_output_tokens` is reserved before dispatch. See [Model routes](/docs/configuration/models/) for current limits. This adapter subset does not imply provider-specific conformance.

## OpenAI-compatible text embeddings

`POST /v1/embeddings` accepts a model alias and one non-empty string or an array of 1–2048 non-empty strings. It optionally accepts `dimensions` (1–65536), `encoding_format` (`float` or `base64`), and a `user` string up to 512 bytes. Token-ID arrays, nested inputs, multimodal input, streaming and extra fields are rejected. The configured route must use provider `openai` or `openrouter` and explicitly declare embedding support; dimension and base64 support are separate opt-in route declarations. OpenRouter embeddings are not inferred from chat support. A missing declaration or unsupported provider returns `501` before durable operation and attempt creation. Errors distinguish basic embeddings, custom dimensions and base64 support; callers can choose an embedding model, omit dimensions or use float encoding as applicable. A successful response uses the public model alias and must include one correctly shaped embedding for each input item. See [Model routes](/docs/configuration/models/) for setup and pricing bounds.

This contract covers the implemented OpenAI-compatible text embedding operation only. The declared route flags are configuration assertions, not conformance results; native Anthropic and Bedrock embeddings, provider-specific conformance suites, and other input modalities are not implemented.

## Automatic gateway activity and task correlation

Every model request admitted to a supported Niu inference route is recorded
automatically with its operation and attempt, public model alias, execution
status, timing, usage confidence, provider-reported token counts and any known
settled customer charge. Request and response content is retained separately
for 24 hours unless explicitly disabled with `x-niu-log-payloads: false`; see
[Request content in Logs](#request-content-in-logs). Missing usage or cost remains
unknown. This is the default source for request activity; a user does not need
to export or import gateway logs.

`GET /admin/v1/organizations/{organization}/projects/{project}/requests/{attempt}`
returns one request's metadata independently of list pagination and filters. It
requires read access to that workspace and returns 404 when the request is absent
from that scope. The response uses the same customer-safe fields as the request
list; Supplier costs are excluded. Payload content is retrieved separately.

`GET /admin/v1/organizations/{organization}/projects/{project}/requests?limit=50`
returns the newest gateway attempts first. Limits range from 1 to 100. Optional
`from_ms` and `to_ms` bound creation time (`from_ms` inclusive, `to_ms`
exclusive); `model_alias`, `key_id`, and `status` narrow the same workspace feed.
Status values are `not_sent`, `may_have_executed`, `confirmed_completed`,
`confirmed_not_executed`, `output_withheld`, and `delivery_failed`. The first four filter Provider
execution state; `output_withheld` selects recorded blocked or indeterminate
output inspection. `delivery_failed` selects recorded delivery HTTP errors
(400–599), independently of Provider execution and customer charges.
`http_status` accepts an exact code from 100 to 599 or `unknown` for absent
delivery status; it combines with the other filters. Unknown does not mean
successful, failed or not charged. The summary's `delivery_statuses` counts
each recorded code and a nullable unknown category across the full selected
range in its consistent read snapshot. A Provider-completed request can still have withheld output
and incurred customer charges. The endpoint returns `data`, a nullable
`next_cursor`, and a `summary` computed over the complete selected filter range,
independent of the current page. Pass the previous attempt UUID as `after` to
continue with older matching entries. Pages are newest first; this is a live
traversal, not a snapshot across pages. It requires workspace read permission or
an installation administrator credential. Each record includes `attempt_id`,
`operation_id`, optional `api_key_id` and `key_name`, optional `task_id`,
optional `task_evidence`, public `model` alias and the nullable
`provider_model` reported by the upstream provider,
`created_at`, `dispatched_at`, `completed_at`,
`duration_ms`, `execution`, nullable `output_guardrail_outcome`,
`usage_confidence`, nullable prompt/completion token
counts, and nullable customer charge currency, amount and status. A null
`output_guardrail_outcome` means no inspection outcome was recorded; it does
not establish delivery or content protection. Token and money
quantities are exact decimal strings. `task_evidence` is the latest supplemental
execution record for the same task ID in this workspace; it includes its scoped
execution ID, source, record ID, coverage assertion and authority/result pairs,
but no imported spans. Fetch metadata-only spans and causal links from
`/admin/v1/organizations/{organization}/projects/{project}/executions/{execution}`
when an operator opens the trace.
Unsettled or unpriced requests can have unknown cost; their absence from a cost
ledger does not mean zero spend.

Request listing and CSV export accept `sort=time_desc` (default), `time_asc`,
`latency_desc`, `input_desc` or `output_desc`. Sorting covers all matching
requests before pagination. Known measurements precede unknown ones; latency
uses complete request timing or historical complete duration, never an
interrupted timing as a complete latency. Time and attempt ID break ties.
Keep the same filters and sort when passing `next_cursor` as `after`.
Traversal is live: measurements completing between pages can move a request
in the ordering. Use CSV for a single-statement view of the selected range.
Unknown sort values return HTTP 400. Customer charges are not ranked across
different currencies.

`GET .../requests/export` downloads customer-safe CSV for the same date, model,
API key and execution-status filters. It reads the range in one database
statement, independently of the paginated Logs page. Workspace read access is
required; inference keys cannot export. The response is an attachment with
`Cache-Control: no-store`. Internal identifiers, task records, payloads,
credentials and Supplier commercial data are excluded. Unknown values remain
empty cells, with usage and charge status alongside them. Token counts and
customer nanounits preserve their exact decimal digits. Formula-like text cells
are prefixed with an apostrophe for spreadsheet safety. Exports over 10,000
requests return `413` with instructions to narrow the filters; they are never
silently truncated. Pagination parameters are rejected.

The range summary reports matched request count, requests with provider-reported
usage, exact prompt/completion token totals, requests with complete timing,
average complete gateway duration, matching P50/P95/P99 latency percentiles with sample count and boundary, reported cache-input/reasoning-output category sums with reported and unknown request counts, unresolved and unpriced customer charges, customer charge
totals by currency, and usage breakdowns by model and workspace API key. A missing price or unsettled attempt remains
unknown and is not converted to zero.

`charges_by_model` and `charges_by_key` report full-range customer ledger amounts
separately by currency, within the same summary snapshot and filters. Amounts
are exact decimal strings in nanos; missing settlement produces null currency
and amount, with separate unresolved, unpriced and not-charged request counts.
These counts and charged requests partition each row's request count. Key
identifiers are API references for scoped drilldowns, not display labels.
These breakdowns contain no Supplier purchase costs or margins.

### Request phase timing

New admitted requests include a nullable `timing` object in the workspace
request feed: `dispatch_ms`, `headers_ms`, `first_output_ms`, `total_ms`,
`complete` and `http_status`. Offsets use a monotonic gateway clock from
request handling, independent of payload capture. First output is measured
from a meaningful streamed Chat event, including text, reasoning, refusal or
tool-call output; role-only events, keepalives and usage records do not count.
Nonstreamed requests leave `first_output_ms` unknown.

Logs draws preparation, first-output wait and output-stream duration on one
scale. Preparation includes validation and admission. Wait includes network
and upstream processing; Niu cannot split those without upstream spans.
Output duration includes delivery and terminal processing, so tokens per
second describes the observed output stream, not pure model compute speed.
Interrupted responses retain an incomplete interval, including cancellation
after dispatch but before headers; `headers_ms` and `http_status` then stay
null. Process crashes and cancellation during admission acknowledgement may
leave phase timing unavailable. Older requests are
not backfilled.

### Request content in Logs

New Chat Completions, Responses and embeddings requests retain content in Logs
by default. Send `x-niu-log-payloads: false` to opt out for a request. In dashboard
Chat, turn off **Save payloads in Logs** in the composer settings before sending.
This does not apply retrospectively to earlier requests.

Captured content is stored separately from accounting records for 24 hours.
Capture is bounded to 1 MB per side; a retained request exceeding the request
capture limit is rejected. Streaming responses are retained as streamed text,
with incomplete and truncated responses labeled. HTTP headers are not retained.
Known credential fields in request objects are removed, including Authorization,
Proxy-Authorization, Cookie, Set-Cookie and API-key header names. Arbitrary secrets
inside prompts are not automatically redacted. Response capture excludes
confidential Supplier cost metadata. Historical JSON and SSE responses are also sanitized when read. If a malformed or incomplete structured response cannot be safely serialized, the read returns HTTP 503 without its raw body; accounting and timing metadata remain available independently.

An authorized workspace reader can fetch retained content with
`GET /admin/v1/organizations/{organization}/projects/{project}/requests/{attempt}/payloads`.
The response contains `data` with `request`, `response`, `content_type`,
`complete`, `truncated` and `expires_at`, or `null` when content was not captured
or has expired. Workspace write permission is required to delete it using
`DELETE` at the same path. Content deletion does not delete accounting records. A durable content-free deletion marker prevents late capture or retries from recreating explicitly deleted payloads. Deletion before capture also prevents that attempt’s content from being stored.

An application or agent adapter can send the same optional `X-Niu-Task-ID`
header on every inference call belonging to one task. Chat completions,
Responses and embeddings accept 1–200 printable ASCII characters. Niu stores
the value as opaque operation metadata and never forwards it to the provider.
Activity without this header is still retained and remains visible as
individual model requests. The header only groups model calls: local tool work,
validation and acceptance need separate adapter events and are not inferred
from gateway traffic.

Task correlation covers only model requests handled by Niu. External model
calls, agent tool events, task acceptance, and subscription usage are outside
Niu's collection scope. Niu does not expose execution or agent-usage import APIs.

## Paired benchmark analysis

`POST /admin/v1/benchmarks/compare` accepts a `PairedExperimentV1` dataset and returns a stateless comparison report. Candidate trials must reference the same declared task snapshot, tool, permission and acceptance-policy hashes and match the pinned route revision. Each trial joins execution-span charge references to supplied Gateway attempt rows by canonical attempt UUID; the evaluator checks task ID, model alias, unique references and that settled attempt sums match trial totals. The evaluator requires explicit opt-in metadata, validator or human acceptance evidence to qualify a completion, complete trace coverage and settled cost evidence for every billable invocation. Unknown prices prevent a paired cost comparison; pricing remains optional for ordinary gateway use. Evaluator cost and unsuccessful work are included in totals.

The endpoint only analyzes supplied records. It does not dispatch requests, enforce the approval metadata, reserve budget, persist reports, isolate task tools, or authenticate the evidence source. The `opt_in` and `authorization_ref` fields are assertions, not security controls. See [paired benchmark analysis](/docs/concepts/benchmarking/) for the CLI, fixture and limits. No real paired experiment has been run by this feature.

## Subscription quota observations

Bootstrap administrators can register supplier account metadata and import provider-reported quota snapshots without proxying inference:

- `POST /admin/v1/organizations/{organization}/projects/{project}/accounts` registers a workspace-scoped account. Provide an opaque `env:` or `secret:` credential reference; the account starts unverified and registration does not enable inference.
- `POST /admin/v1/organizations/{organization}/projects/{project}/accounts/{account}/quota` accepts a version 1 `QuotaObservationV1` sample. An exact replay returns the original observation ID; a conflicting payload for the same account, window, and timestamp returns `409`.
- `GET .../accounts` lists account metadata without returning credential references. `GET .../accounts/{account}/quota` returns the latest sample per provider window, including its freshness, validity deadline, reset time, and previous sample baseline.
- `DELETE .../accounts/{account}/quota?window_key=weekly` permanently removes all imported samples for that account window, including the comparison baseline. The response reports the number deleted; repeating the request is safe.
- `GET .../accounts/{account}/executions` lists metadata-only tasks with charge references matching attempts assigned to the account, up to 100 records.

The `Subscriptions` dashboard page displays provider-reported units as reported and marks changes between snapshots as unattributed. It does not infer token amounts from percentages or claim that a quota delta was caused by one task. When an execution span's `charge_ref` exactly matches a Niu attempt UUID assigned to an account, task and account views link to each other without exposing execution payloads in the account index. Other charge namespaces remain unresolved. Latest and previous BIGINT quantities are decimal strings for exact browser display. Imports only persist observations: they do not refresh credentials, forward inference, change subscriptions, or reset provider allowances. These endpoints accept scoped operator credentials with the required read/write permission, or installation bootstrap credentials. Quota collection also accepts scoped collector keys; native provider collectors remain unimplemented.

The current gateway milestone is limited. This reference grows with tested endpoints; it does not claim parity with every LiteLLM operation or provider today.

## Platform upstream cost reporting

Installation administrators can read persisted platform upstream accounting for a workspace. These compatibility endpoints are procurement controls, not customer billing APIs. Ordinary workspace sessions and Supplier memberships do not grant access.

- `GET /admin/v1/organizations/{organization}/projects/{project}/budget` returns `data` with currency, lifetime limit, reserved exposure and settled cash spend, or `null` when no budget exists.
- `GET /admin/v1/organizations/{organization}/projects/{project}/costs?limit=50` returns settled entries and a nullable `next_cursor`. Pass that UUID as `after` to continue; limits range from 1 to 100.

All monetary and token values in these responses are decimal strings to preserve 64-bit integer precision in browser clients. Monetary amounts use billionths of the named currency. Each entry retains its attempt and price revision, separate API-equivalent and cash costs, token evidence, and a flag for usage exceeding reserved bounds.

Pages traverse ascending attempt UUIDs, not chronological order. This is a live view: newly settled entries may require a fresh traversal. Unsettled attempts are excluded; an empty page does **not** prove zero cost. Reserved exposure remains visible in the budget. Subscription fee allocations and capacity reports are not yet included.

Reporting requires installation administration even when the caller has workspace read permission. The reporting endpoints do not create prices, settle attempts, or enable automatic gateway pricing. Customer-facing request charges, Usage and Billing are serialized separately and never substitute these upstream amounts for customer charges.

### Create a platform upstream budget

Send `POST /admin/v1/organizations/{organization}/projects/{project}/budget` with an administrator token and a body such as:

```json
{"currency": "USD", "limit_nanos": "100000000000"}
```

This creates a USD 100 lifetime upstream budget for the workspace. It does not set a customer charge limit or an invoice amount. Amounts must be nonnegative decimal integer strings, with no exponent or fractional notation, within the signed 64-bit range. Currency is a three-letter uppercase code; no currency conversion is performed. Concurrent creation has one winner; an existing budget returns 409 without changing its limit, reservations or spend.

**Current admission behavior:** supported priced routes reserve their configured input/output bounds before dispatch; insufficient funds or a missing matching-currency budget prevents the upstream call. Once a workspace has an upstream budget, shared-route dispatch requires a trusted held reservation. Unpriced shared requests without such a reservation are rejected. Authorized owner-funded personal Chat and video routes are excluded from platform procurement accounting; their current permissions and Guardrails still apply. Existing dispatched attempts are not retroactively reserved. Provider billing bounds still require qualification: understated bounds can produce an overrun, which is recorded as liability. This is not a universal guarantee against upstream billing outside those bounds. Customer Usage does not expose procurement-budget management.

## Installation vendors

Shared upstream connections persist in PostgreSQL and are managed with installation authority or an explicitly granted platform-administrator role:

- `GET /admin/v1/vendors` lists all configuration metadata, including disabled configurations, without credentials. Optional `supplier` filters by explicit Supplier business ownership. The response is one unpaginated `data` array without a silent row cap; memory use grows with list size.
- `POST /admin/v1/vendors` creates a vendor with a write-only `api_key`.
- `PUT /admin/v1/vendors/{id}` updates metadata, enabled state or the credential using `expected_revision`.
- `GET /admin/v1/vendors/{id}/models` lists all of the vendor's mappings, including disabled mappings, in alias order. This compatibility endpoint returns one `data` array without pagination; it does not silently truncate at 1,000 rows. Large lists still consume response memory proportional to their size.
- `POST /admin/v1/vendors/{id}/models` creates a mapping without a revision or updates it using the current `expected_revision`.
- `POST /admin/v1/vendors/{id}/check` with `{ "alias": "team/fast" }` performs a non-inference `GET /models` check. The check is capped at five seconds and 2 MiB, blocks redirects and private-network destinations, and returns only a status plus whether the exact upstream model ID appears in the provider catalog. Provider response content and credentials are never returned. A catalog listing does not prove inference access or quota; use Chat to test a real request through Niu.

A Supplier can own multiple independently configured credentials, and each credential can bind multiple model aliases. Workspace key grants apply to each requested alias even when aliases share a credential. See the [current multi-key and multi-model verification](https://github.com/niu-io/niu/blob/main/docs/reference/supplier-key-isolation-live.md#multiple-mappings-on-one-credential--current-input-verification) for the exercised update, disable, restart and billing behavior.

On a model update, omitting `pricing` preserves its exact stored value; explicit `null` clears it. Stale updates return `409`. Responses use `Cache-Control: no-store`. Ordinary organization and workspace roles cannot administer these platform resources without an explicit platform-administrator grant. See [Model routes](/docs/configuration/models/) for encryption, precedence and bootstrap behavior.

## Durable Video submission intents

The actor-owned workspace `video-intents` API saves a validated text-video request
before explicit submission. `PUT /{intent}` saves a fresh identity, `GET /{intent}`
restores its content and original job/preparation state, and `POST /{intent}/submit`
explicitly submits or replays it with `expected_revision`. The collection GET
provides a scoped metadata index; DELETE clears content while retaining a

charge or reservation can be released.

and status code in workspace request diagnostics. The create response remains

## Operation-scoped request diagnostics

`GET /admin/v1/organizations/{organization}/projects/{project}/requests` and
its `/export` CSV endpoint accept optional `operation_id` (UUID). The filter
selects execution attempts belonging to that operation within the authorized
workspace; list summaries use the same filter. An unknown operation or one in
another workspace yields no matching rows. Invalid UUID syntax returns 400.
Other filters combine with it, and existing pagination/export limits still apply.

Use the `operation_id` returned by request metadata for correlation; keep internal
identifiers out of product display labels. The JavaScript SDK exposes this as
`operationId` in `listGatewayActivity` and `exportGatewayActivity`. This read-only
filter does not initiate retries. Nullable `retry` metadata supplies each attempt’s ordinal, predecessor, maximum attempt count and policy revision.

## Minimum text request charge

Customer tariff publication accepts optional `minimum_charge_nanos`, an exact
nonnegative decimal string within signed 64-bit range. A new tariff defaults to
zero; replacing an existing nonzero minimum requires an explicit value, and
`"0"` disables it for future requests. Null and malformed amounts are rejected.

Known completed usage costs the greater of the rounded token amount and this
minimum. Admission reserves the greater of the token bound and minimum, including
when token rates are zero. Unknown usage remains unresolved; a client disconnect
does not authorize charging the minimum or releasing its outstanding reservation. Existing history is
not repriced, and this field does not configure Supplier or video charges.
Invoice lines and model-price reads expose the pinned/current minimum as
appropriate. Internal balance refunds remain bounded by the original charge,
restore the refunded key allowance once and preserve historical invoice pricing. The SDK uses the same `minimum_charge_nanos` field. See the
[contract and actual verification](https://github.com/niu-io/niu/blob/main/docs/reference/text-minimum-charges.md).

## Customer text fixed request fees

Customer tariff publication now accepts `request_fee_nanos` as an exact
nonnegative integer string. A known completed request is charged the greater of
its rounded token amount plus this fixed fee and `minimum_charge_nanos`. Admission
reserves using the same formula; rejected or unresolved requests do not invent a
fee. Historical tariff versions remain pinned. Replacing a nonzero fee requires
an explicit value, and `"0"` disables it. The SDK uses the same field.
See the [pricing rule and supported boundary](https://github.com/niu-io/niu/blob/main/docs/reference/text-request-fees.md).


Current-input fixed-fee verification now includes buffered and streamed Responses,
Chat/Responses/embeddings sharing one account concurrently, and bounded idempotent
internal refunds. Independent provider-response arithmetic and database ledger
reads agreed; restart retained the charges and restored allowance. See the
[protocol and refund evidence](https://github.com/niu-io/niu/blob/main/docs/reference/text-request-fees.md#refund-responses-and-mixed-protocol-verification).


Fixed-only pricing was also exercised with two gateways and workspaces competing
for company credit sufficient for one request: one completion, one HTTP 402 and
one exact debit. A separate SIGKILL after actual streamed content retained unknown
usage and its reservation without inventing a fixed-fee charge or retry. See the
[contention and crash evidence](https://github.com/niu-io/niu/blob/main/docs/reference/text-request-fees.md#shared-credit-contention-and-interrupted-fixed-fee-liability).


Fixed-fee admission rejects a token-plus-fee amount that overflows signed 64-bit
nanounits with HTTP 400. A representable amount without sufficient spending
capacity returns HTTP 402. Actual API requests and independent SQL verified that
neither case dispatched upstream or left financial reservations; see the
[admission boundary evidence](https://github.com/niu-io/niu/blob/main/docs/reference/text-request-fees.md#checked-addition-at-admission).

`request_fee_nanos` are per-request currency nanounits. Keep every amount as a

## Cached input with fixed request fees

When `cached_prompt_rate` is set, price uncached input, cached input and output
separately, sum their exact amounts and round upward once. Then add
`request_fee_nanos` and apply `minimum_charge_nanos` to the combined amount.
Missing required cached usage remains unresolved; a fixed fee does not replace
the missing evidence. All rates and fixed amounts retain their pinned revision.

Actual nonzero-cache completions exercised both an additive fee and a minimum
above the combined amount. Saved provider usage and reopened database records
matched the charges, invoice and refund balance. See the
[formula and verification scope](https://github.com/niu-io/niu/blob/main/docs/reference/cached-input-pricing.md#cached-tokens-combined-with-fixed-fees-and-minimums).


## Immutable Supplier quotes

membership in that Supplier is required; company ownership grants no access.
The Supplier, offer and revision must match. Missing or inaccessible quotes
return 404. The JavaScript SDK exposes `getSupplierOfferRevision`.

Text rates remain exact strings, with nullable cached-input pricing. Media

Reading a quote does not activate or qualify it. Keep procurement information

four saved text revisions; active Supplier viewer access, company-role denial

### Discovering Supplier quote revisions

`GET /admin/v1/providers/{provider}/offers/{offer}/revisions` lists historical

`next_before` as `before` while `has_more` is true. Each entry adds `is_current`;

## Upstream credential request limits

Platform administrators can read or update
`/admin/v1/vendors/{vendor}/request-rate-limit` and read its `/history`.
PUT requires `requests_per_minute` (explicit null for unlimited, zero to stop
dispatch) and the exact string `expected_revision`. Limits are independent of
customer key RPM and shared across gateway instances using the same saved
credential. History supports `before_revision` and `limit`.

A local dispatch refusal returns 429, `upstream_request_rate_exceeded` and a
conservative `Retry-After: 60`. It does not send another upstream request.
The SDK provides `getVendorRequestRateLimit`, `setVendorRequestRateLimit` and
`listVendorRequestRateLimitHistory`. See the

## Upstream credential cooldown

Platform administrators can read
`GET /admin/v1/vendors/{vendor}/cooldown`, or use SDK `getVendorCooldown`.
The response reports `policy_revision`, `failure_threshold`, `window_seconds`,
`cooldown_seconds`, `active`, nullable `cooldown_until`, and
`qualifying_failures`. Company-scoped administrators cannot read this state.

Three new, qualified canonical OpenRouter text authentication refusals in a
60-second rolling window pause new selection for 60 seconds. Further qualifying
in-flight failures may extend the deadline. Timeouts and uncertain execution
never count. Direct selection returns `503 upstream_credential_cooldown`; a pool
with no eligible mapping returns `503 route_pool_unavailable`. Pinned requests
continue. State survives restart and credential edits; expiry restores
eligibility automatically without an upstream probe or administrator republish.
This fixed policy has no write endpoint. See the
[policy and verification boundary](https://github.com/niu-io/niu/blob/main/docs/reference/upstream-credential-cooldown.md).

### Authentication failure and unresolved charges

A 401 does not universally prove that a Provider did no work. Managed text
requests pin the reviewed canonical OpenRouter nonexecution policy at admission;
custom endpoints using the same adapter and older requests without that policy
retain uncertainty and their applicable holds. Customer diagnostics preserve the
HTTP failure separately from execution and charge state. Do not treat every 401
as a refund or permission to retry.

See [qualified nonexecution policy](https://github.com/niu-io/niu/blob/main/docs/reference/qualified-nonexecution-policy.md)
for the implemented boundary and actual verification.
