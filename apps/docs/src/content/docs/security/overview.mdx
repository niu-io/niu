Niu separates account sign-in, workspace access, application API keys, and platform administration.

## Credential ownership

Provider credentials remain server-side. Managed Supplier credentials are encrypted in PostgreSQL with AES-256-GCM using `NIU_VENDOR_ENCRYPTION_KEY`, held separately in the deployment secret store. Only platform administrators can manage these shared connections; organization or workspace members cannot. Management APIs never return provider credentials. Back up the encryption secret separately from database backups; automatic master-key rotation is not implemented. Startup validates every retained Supplier inference credential against its Supplier identity in bounded pages, including disabled Suppliers and those with no model mappings. A wrong key or undecryptable credential prevents startup; disabling a Supplier does not bypass validation. This check does not re-encrypt records or qualify master-key rotation for other encrypted data. Public model names resolve through approved routes; requests cannot override provider, credential, or endpoint settings. Logs and browser responses must not contain secrets.

## Authorization

Inference API keys have explicit model grants, workspace ownership, expiry and revocation. Administration accepts the configured `NIU_ADMIN_TOKENS` bootstrap secret and persistent operator session tokens. Bootstrap tokens have installation authority. Each operator belongs to one organization and may be limited to one workspace. Within that scope, `owner` manages operators and can read or write management resources, `admin` can read and write those resources, and `viewer` can read them. A workspace owner cannot grant organization-wide access or access to another workspace. A workspace slug in a URL is presentation state; the server enforces the credential's actual scope.

`GET /admin/v1/session` returns the authenticated operator's scope and role permissions, or identifies an installation bootstrap credential. The dashboard uses this response to present available actions. Every API call checks authorization again, so hiding or enabling a control does not grant authority. Private API responses are marked `Cache-Control: no-store`.

Upgrading from unscoped operator credentials revokes those legacy operators and sessions. Use an installation bootstrap credential to create replacement operators with explicit organization or workspace scope.

## Account sign-in

When password sign-in is configured, members sign in with their email and password. Their role determines which actions they can perform within their organization or workspace. The Dashboard restores the server session through a Secure, HttpOnly cookie and does not save a bearer token in browser storage. Sessions expire after eight hours. Signing out revokes the current session.

Members can change their password in **Settings → Account**. A successful password change revokes all of that member's sessions and requires signing in again. Self-registration and OIDC/SAML are not implemented. Hosted password sign-in requires the configured HTTPS origin; real HTTPS browser qualification remains unfinished. See the [sign-in API contract](/docs/reference/api/#operator-roles-and-sessions) for configuration, provisioning, and throttling.

Owners can also issue scoped operator session tokens for API administration. These tokens are returned once, stored only as SHA-256 hashes, and rejected after expiry or revocation. Their lifetimes range from 60 seconds to one year. Revoking a member revokes all their sessions; an individual session can also be revoked. These bearer tokens are distinct from the Dashboard's browser session. Operator and session lifecycle writes append immutable, metadata-only audit events.




## Data handling

Every protocol adapter must document what request and response data it transforms, buffers, records, or sends to a provider. Streaming behavior and output inspection need explicit limits and failure semantics.

## Development account initialization

The explicitly enabled loopback development login uses the same first-use
workspace initializer as the setup API. A new default workspace receives a USD
customer balance account with zero funds and zero approved credit. Starting the
login service before calling setup does not bypass prepaid account creation.
This creates no payment receipt and grants no spending capacity.

An existing default workspace keeps its saved billing configuration, including
legacy workspaces without a balance account. Restart does not reset a saved
member's password, role or revocation. Converting a legacy workspace to prepaid
billing remains an explicit administrative operation.


## Platform grants and customer roles

An explicit platform-administrator grant is separate from the member's role in
a customer company or workspace. Platform-only Supplier, route-pool, branding,
payment support-inventory, payment-configuration and media-pricing handlers check that grant after session
authentication; they do not require the member to be a customer-company owner.
An ordinary company owner has no platform authority without the explicit grant.

Customer endpoints continue to enforce the member's original role and tenant
scope. Platform administration does not grant access to another workspace's keys,
requests or balances, nor does it allow a customer viewer to create workspaces.
Installation-only financial policy operations remain installation-only. Grant
changes are read on authenticated requests, so revocation removes platform access
from an existing session without granting or removing its separate customer role.

Saved payment configuration is also authenticated and decoded before the Gateway becomes ready, including disabled configurations and installations with no Supplier records. Missing or incompatible master keys prevent startup without changing the saved ciphertext or exposing merchant settings in diagnostics. Restore the matching key; this guard does not re-encrypt records or implement master-key rotation.
