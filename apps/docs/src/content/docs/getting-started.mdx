Send your first request through Niu using a workspace API key and a configured model.

## Set up model access

1. **Start Niu.** Follow the [deployment guide](/docs/deployment/single-container/), or run `pnpm dev` for local development.
2. **Open the dashboard.** Sign in with your account. For local development, use the account configured by the launcher.
3. **Connect a Supplier.** Choose its Provider adapter, save its API credential, and configure model routes using the [model route guide](/docs/configuration/models/). Confirm your route appears in **Models**.
4. **Create an API key.** Select a workspace and open **API keys → New API key**. Enter a name and expiration, then select **Create key**. The key can call every model route available in the workspace. Copy its secret now; it cannot be retrieved later.

## Make a request

Use your workspace key and a model alias from **Models**. The example below uses
`fast`, the alias in the example container configuration. Replace it with your
configured alias.

```sh
export NIU_API_KEY='your-issued-client-key'
curl http://localhost:2555/v1/chat/completions \
  -H "Authorization: Bearer $NIU_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"fast","messages":[{"role":"user","content":"Hello"}]}'
```

The base URL for compatible clients is `http://localhost:2555/v1` in the container,
or `http://127.0.0.1:2566/v1` in development. Replace `fast` with the actual alias
available in your workspace when using a dashboard-managed route. The key dialog
provides the base URL and a client example for your running installation.

Open workspace **Logs** to inspect status, timing, reported tokens, and retained
request and response payloads. **Usage** shows consumption and customer charges.
See [request logs](/docs/concepts/execution-observation/) for capture and retention settings.

Applications authenticate with workspace keys. Keep Supplier credentials and
installation administrator tokens on the server.

For repository setup, requirements, and build commands, follow

## Current limitations

- Container installations use an administrator credential for initial setup and can issue scoped member sessions. The opt-in [password session API](/docs/reference/api/#operator-roles-and-sessions) supports provisioned members and session restoration behind the configured HTTPS origin. Self-registration and real HTTPS browser qualification remain unfinished.
- Configuring a route does not qualify its upstream capabilities or supply rights. File-managed deployments can configure routes in `config/niu.example.toml` instead of the dashboard.
- Request and response payloads are retained for 24 hours by default. Disable capture per request with `x-niu-log-payloads: false` or turn off **Save payloads in Logs** in Chat settings. Expired or uncaptured content is unavailable; request metadata remains. Missing token usage, timing, or customer prices remain unknown.
- Budgeted workspaces require a supported bounded reservation before dispatch; unpriced requests cannot bypass that requirement. See [model pricing](/docs/configuration/models/#optional-text-route-pricing). Upstream billing bounds still need qualification.
