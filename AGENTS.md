# Niu public repository

Write product documentation in English. Keep the Niu brand assets and theme tokens. The product name is Niu in English UI and documentation, never niu.io or NIU.IO. Keep niu.io only as the domain in URLs and technical configuration. Use 牛元 as the Chinese brand name in Chinese-language content (Niu 牛元 when paired with the English brand); 牛刀 is the retired name.

Keep marketing source in the separate `niu-io/website` repository. Niu owns the public catalog, dashboard, docs and APIs; the hosted distribution composes their pinned artifacts under the single `niu.io` domain. Do not introduce a separate application subdomain or make community builds depend on website or private source. Follow `docs/architecture/repository-ownership.md` for route and asset ownership.

This repository contains only Niu's public project. Internal research, enterprise source, private issue URLs, local source paths, customer records, and secrets must not enter the public tree. Retain upstream copyright and license attribution for selectively reused code.

The implementation reuses individual source modules, not a complete upstream repository or its history. Keep each imported module small, traceable, independently licensed, and explicit about behavior that remains unimplemented.

## Agent-oriented product direction

Follow [product principles](docs/product/agent-oriented-principles.md) and the [documentation contract](docs/development/agent-documentation.md) when changing product, integrations, docs or marketing. Niu is **The Model Platform for Agents**: it supplies trustworthy information and authorized model-management capabilities. Coding agents own task completion and quality/cost decisions; Niu does not promise optimal value or task success. Invocation is only one part of model management.

Design direct agent discovery, operation, verification and recovery. Humans set goals and authority and review important changes; do not make them relay machine-readable information. Keep required human reading to orientation and agent-led onboarding. Other references primarily serve coding agents; model trials and request/performance/cost inspection remain useful human surfaces. Host-native coding-agent plugins complement MCP and share its underlying contracts; distinguish them from server-side Niu plugins and distinguish host hooks from platform events. Label planned capabilities and current authorization limits explicitly.

## Work tracking and review follow-up

Use **Beads (`bd`) as the primary work tracker**, especially for tasks discovered during code, API and UX reviews. Run `bd prime` at session start and after compaction; use `bd ready`, `bd show <id>` and `bd update <id> --claim` before starting tracked work. Use a distinct public-safe `BEADS_ACTOR` for each concurrent worker. Keep task ownership, priority, dependencies, progress, blockers and acceptance evidence in Beads. See [the workflow](docs/development/beads.md) for setup, synchronization and handoff.

Before creating a review task, search for the existing finding/reference and update or reopen it rather than duplicating it. Record the trigger, impact, source/revision, evidence limits and observable acceptance criteria; link related findings and use blocking edges only for real prerequisites. Revalidate older findings against the current implementation before changing code. A review-only request permits review records and task capture, not product implementation.

Markdown holds durable requirements, review evidence, design decisions and dated verification records; link those records to the bead. Do not maintain a second live backlog, owner/status table or TODO checklist in Markdown. Historical review statuses remain dated evidence, with current execution state in Beads. Use GitHub Issues only when explicitly requested or needed for external/public discussion; link them to the bead instead of mirroring the backlog or automatically publishing review findings.

Keep a task open while implementation awaits verification; use a `needs-verification` label when useful. Close it only with evidence matching its acceptance scope, or an explicit duplicate/rejected/superseded disposition. In the handoff record completed work, unverified behavior, blockers and the next action. Commit the Dolt working set, refresh the portable issue snapshot, and commit and push verified changes unless the user asks to keep them local; report any unpushed state honestly. Keep changes scoped to the active task.

## Branch model and production promotion

Branch every product change from the current `release/<minor>` branch (currently `release/0.3`), merge verified work back into `release/<minor>`, and push `release/<minor>` to `origin`. `main` is production and receives only a staging-accepted `release/<minor>`; never commit product changes to `main` directly, and never force-push `main` or a release branch. Create release tags on the release branch after staging acceptance. See [the branch model](docs/development/branching.md) for the flow, staging gate and cleanup rules.

## Dashboard choice controls

Legacy links to tabbed platform settings must open the matching canonical tab with its sibling navigation visible, preserving other query parameters and the fragment. New entry points link directly to the canonical tab.

Never use a native HTML `<select>` / `<option>` control, the shadcn Select component, or a hand-built Select/Dropdown abstraction anywhere in the product UI. This is a hard design rule, not a preference. Compose the installed shadcn `DropdownMenu`, `DropdownMenuTrigger`, `DropdownMenuContent`, and the appropriate menu item primitives directly at each call site for choice menus, including single-choice form fields, workspace/model selectors, and filters. Use the shared menu primitives' icon gutter and spacing; do not override their internal layout with local CSS. Single-choice and multiple-choice items show the selected state as a check on the right, with text and optional icons aligned to ordinary action items. Keep Radix radio/checkbox semantics; do not add a left radio dot or an extra selection column. See `docs/ux/menu-review-2026-11-01.md` for the agreed convention and audit evidence. Verify each changed menu in the browser, including open state and alignment, before reporting completion.

Customer access lists expose one setup action in the tab content. Keep balance policy with billing and describe an empty member list in terms of members.

Customer access lists retain workspace links, member roles and workspace scope on narrow screens. Show labeled values within each row without horizontal scrolling.

Customer and API key directories keep their primary creation action visibly labeled at every width. The key directory shows one creation action even when an active filter hides historical keys.

Do not substitute raw native buttons, text fields, checkboxes, textareas, or data tables where the corresponding shadcn component exists. Keep custom components for Niu-specific behavior, page compositions with no shadcn equivalent, and branded assets. When a needed primitive is missing, install it with the shadcn CLI before considering a custom implementation.

## Dialogs and page simplicity

Registration policy and the registration review queue link directly to each other within their owning Settings and Customers tabs. Display the pending count on the review action when positive.

Follow [the UI consistency standard](docs/ux/ui-consistency-standard.md) for all dashboard pages, dialogs, choice controls, composers, loading states, and visual tokens. Keep management and detail pages as scannable reading and inspection surfaces (tables or concise single-panel key-value summaries) without multi-card sprawl or walls of explanatory prose. Every page-level create, edit, rename, publish, limit-setting, and destructive confirmation action must open an installed shadcn `Dialog` (`DialogHeader`, bounded scrollable body such as `max-h-[90dvh] overflow-y-auto`, and `DialogFooter` with cancellation and primary submit actions, restoring focus to its trigger via `onCloseAutoFocus`). Never replace a read view in place with an inline edit form, embed permanent mutation forms inside a summary page, or expand inline confirmation strips on pages. Conversely, never open a nested `Dialog` inside an already-open modal (such as the global `Settings` dialog); keep secondary flows inside an active modal inline or in-dialog views. Never collapse an open dialog's form or detail frame into a full-body skeleton or raw loading paragraph while fetching choice options or secondary metadata; keep the frame stably mounted and show loading inside the affected control or data region.

A filtered registration queue with zero results shows the relevant empty title. Omit raw submission URLs and generic audit explanations.

Localize billing request counts as complete phrases so each language controls the order of the count, noun and settlement status.

A tab that groups multiple entity types must not show an unlabeled count for just one type. Keep counts with the entity they describe.

## Icons

Use only Lucide React and Tabler Icons for product controls and navigation. Choose icons for their meaning; both libraries are allowed. Keep navigation size, stroke weight and alignment consistent, and use the same icon for the same feature across the sidebar and account menu.

Consider Tabler alongside Lucide when choosing icons. Generations uses Tabler `sparkles`; Chat sessions use Tabler `message-chatbot`; `sparkle-highlight` is another suitable candidate for generative AI actions. Do not limit icon selection to Lucide or add Phosphor or IconPark.

In narrow headers, truncate the parent breadcrumb before clipping a short current page title. Keep the workspace picker and page actions reachable.

After a registration queue refresh or review decision, the queue, customer tab and navigation badges reflect the same pending count, including zero.

## Workspace terminology

Use **workspace** consistently for Niu's customer-facing scope. Do not call the same Niu entity a **project** in product UI, guidance, or generated setup commands. Keep legacy `project` / `project_id` names only where required by existing API, database, or compatibility contracts; translate them to workspace terminology at the product boundary.

## User-reported issues are global requirements

Audit history distinguishes an empty filtered result from an empty journal. Clearing filters resets the category and query together and returns focus to search.

Treat every defect or UX/engineering complaint raised by the user as a **global product requirement**, never as a one-off local patch. For every user-reported issue:

1. Identify the shared root cause in the underlying UI primitive, base stylesheet, backend contract, or operational workflow.
2. Fix the default behavior so the same class of defect is prevented structurally across the entire product, and sweep the whole repository to clean up every sibling occurrence.
3. Codify the resulting invariant in `AGENTS.md` and [the UI consistency standard](docs/ux/ui-consistency-standard.md), and add an automated regression test (e.g. [PrimitivesConsistency.test.tsx](apps/dashboard/test/ui/PrimitivesConsistency.test.tsx) or Rust integration tests) so future changes cannot reintroduce it.

Standing global invariants established from user feedback:

- **Card-free, vertically centered, spacious empty placeholders**: `<Empty>` must stay transparent and card-free (`bg-transparent`, no `bg-card` / `bg-muted` card slabs, no `rounded-[var(--radius-panel)]`, no decorative shadows) across sidebars, drawers, dialogs, embedded sections, and full-width management pages. Full-page empty states (including Guardrails, Events, Routing, Evaluations, and Registrations) MUST optically center in the remaining viewport height via the shared flex canvas rules in `apps/dashboard/app/styles/surfaces.css` (never trapped in the upper half by hardcoded `min-h-[...]` caps or `flex: 0 0 auto` overrides) and breathe comfortably using `<Empty>`'s spacious defaults (`gap-5`, 16px `leading-snug` title, 14px `max-w-[36rem]` `text-balance` relaxed description, and `max-w-xl` action row so 2–3 buttons align on one horizontal row with clear primary/secondary hierarchy instead of cramping inside `max-w-sm`). Narrow rails (such as Generations `Sessions`) override with compact padding and an unboxed muted icon (`EmptyMedia` default variant). Empty-state descriptions may identify a prerequisite. Omit instructions that simply restate the adjacent action labels.
- **Default-safe form and dialog field spacing**: `<Label>` must use CJK-safe line height (`leading-snug`, never `leading-none`). Every labeled field in forms, dialogs, and popovers pairs `<Label>` and its control inside an explicit `grid gap-2` (or `space-y-2`) container with uniform label weight and control height, backed by the zero-specificity CSS field-spacing safeguard in `apps/dashboard/app/styles/foundation.css` so text and controls can never overlap by default. Registration validation focuses the first invalid field and associates the inline error with that control. Editing an unrelated field preserves the error.
- **Staging post-test data hygiene**: Whenever tests or verification run against staging, clean up all created test customers/organizations, test workspaces, test operators/API keys, and test request/billing debris upon completion while preserving baseline staging configuration (default workspace, staging admin/demo logins, Providers, Vendors, Offers, and Standard Prices). Disable temporary upstream qualification connections after verification and confirm their aliases have disappeared from the customer catalog. Preserve prior request and settlement records.
- **Prerequisite-aware entry points and in-place resolution**: Never route a user into a workspace surface whose required prerequisite is known to be absent (for example, directing a workspace with `active_key_count === 0` from Overview or Models into Playground/Generations without surfacing the missing API key first), and never open an empty selector dropdown as an error response when a required resource is missing. Always guide the user honestly according to their permissions and, when they have write permission, provide a 1-click in-place resolution (such as auto-creating a revocable default `"Playground"` API key with explicit user confirmation) alongside custom setup so they never bounce through dead-end detours. Present default and custom key setup together in the confirmation dialog. A composer that opens this dialog needs only one setup action. Empty workspace Logs and Usage link writers directly to key creation when no key is active. Readers see the missing prerequisite without a mutation action. Filtered empty results offer filter recovery. On workspace Overview, expose a prerequisite action once. Keep the primary action visibly labeled on phones and use status counts to inspect the underlying resources. Direct video-mode links open the Video composer and its existing availability or setup state. A saved session retains its own workflow.
- **Viewport-appropriate information density over rigid single-column sprawl**: Full-width canvas utilization means never trapping pages inside an artificial centered column — it does NOT mean stretching individual browsable items awkwardly across 1400px–2560px of horizontal space, nor cramping cards below readable widths. Browsable item directories (such as the public and workspace Models catalog and `CardGridSkeleton`) MUST render as a responsive multi-column card grid (`repeat(auto-fill, minmax(min(100%, 352px), 1fr))`) so desktop viewports display 3–5 comfortable, equal-height cards per row without truncating model titles, wrapping 4 capability badges, or clipping model IDs, collapsing cleanly to 2 columns on tablet and 1 column on mobile. Every UX review must evaluate real spatial ergonomics, scan density, and viewport fit rather than checking rules mechanically.
- **Unified docs shell and zero unscoped third-party CSS**: Never embed third-party full-viewport SPA widgets with unscoped global stylesheets (such as `@scalar/api-reference-react`) inside the Starlight documentation shell, and never hide `.sidebar-pane` or shift the top header on a documentation subroute. Interactive API debugging belongs natively inside the shared Niu docs shell using installed shadcn primitives (`OperationTryIt` on `/docs/api/rest/<slug>/` pages and `ApiExplorer` on `/docs/api/explorer/`) so styles, navigation, light/dark themes, and `<ClientRouter />` transitions stay 100% cohesive with zero cross-page CSS bleed.

- Monetary and credit text pricing editors share the same context bands. The base band starts at zero. Additional bands start at strictly increasing positive whole-token counts, with at most 32 additional bands.
- **Default Standard Pricing aligned 1:1 with Provider rates and zero false `below_cost` alerts**: Default customer standard prices MUST match the Provider's standard price (`100%`, no discount) across every dimension (`prompt_rate`, `completion_rate`, `cached_prompt_rate`, `cache_write_prompt_rate`, `reasoning_completion_rate`, and `context_tiers`), repairing any stale below-cost standard price during Provider sync and prefilling Provider rates when manually publishing text prices. Equal unit rates (`100%` no discount, `sell == purchase`) and inactive/unsupplied routes (`active_supply_routes === 0`) MUST NEVER trigger `below_cost` (`低于采购成本`) warnings. For active supply with comparable rates, use the exact saved selling and purchase amounts in each band. A zero selling rate against a one-nanounit purchase rate has a negative unit spread.

A catalog model can be labeled free only when the complete applicable tariff establishes zero charges, including all token categories, context tiers, the request fee and the minimum charge. Show positive per-request charges alongside token rates.
- **Atomic single-transaction multi-entity onboarding and `expected_revision` provisioning safety**: Never implement multi-entity provisioning (such as creating a customer organization, `Default` workspace, owner sign-in credential, and initial trial credit, or creating an organization/workspace member with sign-in credentials) as sequential client-side mutations that can fail halfway and leave orphaned organizations or passwordless operators. Backend onboarding endpoints (`POST /api/v1/admin/customers` and `POST /api/v1/members` with optional `email` + `password`) MUST validate uniqueness and commit all rows inside a single PostgreSQL transaction (with `Idempotency-Key` replay), rolling back 100% on duplicate email (`409 registration_email_exists`) or validation errors. `PUT /api/v1/members/{operator}/password` MUST treat `expected_revision: 0` identically to `null` / omitted when provisioning an unconfigured member (`revision` becomes `1`) and return `409 registration_email_exists` (never generic `conflict`) when an email belongs to another account.
- **Ordinary 8-character password requirement across all surfaces**: Member, setup, registration, and administrator-provisioned passwords enforce a standard security threshold of **at least `8` Unicode characters and at most `1024` UTF-8 bytes** (`MIN_PASSWORD_CHARACTERS = 8`), preserving spaces and Unicode without imposing 15-character passphrase minimums or artificial character-class regex hurdles. Keep Rust storage, gateway handlers, OpenAPI schemas, SDK client checks, UI hints, and documentation synchronized to `8` characters.
- **Top-down causal form hierarchy and non-destructive per-entity state across modes**: Multi-mode creation and configuration dialogs MUST place the primary mode/type selector (such as Customer `Account type` `Personal account | New organization | Join organization`, `Credit mode`, or `Pricing input mode`) at the **top** of the form using explicit `aria-pressed` `<Button variant="outline">` choices before any mode-dependent fields — never buried at the bottom below a divider where switching modes mutates fields above the user's cursor. Forms spanning multiple semantic entities (such as an organization and a person/owner/member) MUST maintain independent state variables and distinct inputs (`organizationName` vs. `personName`), preserve all user-entered fields across mode switches without clearing or overwriting them, and pass `personName` (falling back to email prefix, never `organizationName`) when creating the owner or member identity.
- **Zero raw database, storage, or transport errors in product UI**: Never render raw SQL/PostgreSQL/ORM/driver strings (`SQLSTATE`, `PgDatabaseError`, `duplicate key value violates unique constraint`, `relation "..." does not exist`), internal storage jargon (`The record is unavailable or its state changed`, `Durable storage is unavailable`), raw HTML proxy pages (`<!DOCTYPE html>`), or raw browser fetch engine strings (`Failed to fetch`, `Load failed`) anywhere in the product UI, and never pass unlocalized English `error.message` strings into Chinese alerts or interpolated notifications. Backend `ApiError` mappings in `apps/gateway/src/error.rs` must classify database integrity/concurrency states into specific error codes with user-safe product copy, and Dashboard transport + shared UI primitives (`authenticatedFetch`, `ApiRequestError`, `route-data.ts`, `ui-locale.ts`, and `<AlertDescription>` backed by `apps/dashboard/app/lib/user-facing-error.ts`) must sanitize and localize all API, storage, and transport failures automatically.

## Navigation hierarchy

Use a single left sidebar for primary navigation; do not add a separate outer product rail alongside the sidebar. Keep the brand mark and workspace switcher in the sidebar header, primary destinations in the main sidebar list, and Docs, Admin access (when authorized), and the account menu in the sidebar footer. For a feature that needs two navigation levels, use sidebar items for the first-level sections and tabs within the selected section for the second level.
