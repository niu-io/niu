# Niu public repository

Write product documentation in English. Keep the Niu brand assets and theme tokens. The product name is Niu in English UI and documentation, never niu.io or NIU.IO. Keep niu.io only as the domain in URLs and technical configuration. Use 牛元 as the Chinese brand name in Chinese-language content (Niu 牛元 when paired with the English brand); 牛刀 is the retired name.

Keep marketing source in the separate `niu-io/website` repository. Niu owns the public catalog, dashboard, docs and APIs; the hosted distribution composes their pinned artifacts under the single `niu.io` domain. Do not introduce a separate application subdomain or make community builds depend on website or private source. Follow `docs/architecture/repository-ownership.md` for route and asset ownership.

This repository contains only Niu's public project. Internal research, enterprise source, private issue URLs, local source paths, customer records, and secrets must not enter the public tree. Retain upstream copyright and license attribution for selectively reused code.

The implementation reuses individual source modules, not a complete upstream repository or its history. Keep each imported module small, traceable, independently licensed, and explicit about behavior that remains unimplemented.

## Agent-oriented product direction

Follow [product principles](docs/product/agent-oriented-principles.md) and the [documentation contract](docs/development/agent-documentation.md) when changing product, integrations, docs or marketing. Niu is **The Model Platform for Agents**: it supplies trustworthy information and authorized model-management capabilities. Coding agents own task completion and quality/cost decisions; Niu does not promise optimal value or task success. Invocation is only one part of model management.

Design direct agent discovery, operation, verification and recovery. Humans set goals and authority and review important changes; do not make them relay machine-readable information. Keep required human reading to orientation and agent-led onboarding. Other references primarily serve coding agents; model trials and request/performance/cost inspection remain useful human surfaces. Host-native coding-agent plugins complement MCP and share its underlying contracts; distinguish them from server-side Niu plugins and distinguish host hooks from platform events. Label planned capabilities and current authorization limits explicitly.

## Work tracking and review follow-up

Use **Beads (`bd`) as the primary work tracker**, especially for tasks discovered during code, API and UX reviews. Run `bd prime` at session start and after compaction; use `bd ready`, `bd show <id>` and `bd update <id> --claim` before starting tracked work. Use a distinct public-safe `BEADS_ACTOR` for each concurrent worker. Keep task ownership, priority, dependencies, progress, blockers and acceptance evidence in Beads. See [the workflow](docs/development/beads.md) for setup, synchronization and handoff.

Before creating a review task, search for the existing finding/reference and update or reopen it rather than duplicating it. Record the trigger, impact, source/revision, evidence limits and observable acceptance criteria; link related findings and use blocking edges only for real prerequisites. Revalidate older findings against the current implementation before changing code. A review-only request permits review records and task capture, not product implementation.

Markdown holds durable requirements, review evidence, design decisions and dated verification records; link those records to the bead. Do not maintain a second live backlog, owner/status table or TODO checklist in Markdown. Historical review statuses remain dated evidence, with current execution state in Beads. Use GitHub Issues only when explicitly requested or needed for external/public discussion; link them to the bead instead of mirroring the backlog or automatically publishing review findings.

Keep a task open while implementation awaits verification; use a `needs-verification` label when useful. Close it only with evidence matching its acceptance scope, or an explicit duplicate/rejected/superseded disposition. In the handoff record completed work, unverified behavior, blockers and the next action. Commit the Dolt working set, refresh the portable issue snapshot, and commit and push verified changes unless the user asks to keep them local; report any unpushed state honestly. Keep changes scoped to the active task.

## Branch model and production promotion

Branch every product change from the current `release/<minor>` branch (currently `release/0.3`), merge verified work back into `release/<minor>`, and push `release/<minor>` to `origin`. `main` is production and receives only a staging-accepted `release/<minor>`; never commit product changes to `main` directly, and never force-push `main` or a release branch. Create release tags on the release branch after staging acceptance. See [the branch model](docs/development/branching.md) for the flow, staging gate and cleanup rules.

## API route naming

Use a single word for each API route segment unless a compound is strictly necessary to preserve meaning or an external compatibility contract. Prefer concise resource nouns and resource hierarchy over concatenated internal type names. Apply route changes consistently to handlers, contracts, SDKs, consumers, tests and generated documentation.

## Remote development

Use SSH for authorized remote inspection and configuration transfers. Do not use Supen to inspect remote sessions or coordinate development unless the user explicitly requests it. Keep transferred credentials outside the public repository.

## Dashboard choice controls

Never use a native HTML `<select>` / `<option>` control, the shadcn Select component, or a hand-built Select/Dropdown abstraction anywhere in the product UI. This is a hard design rule, not a preference. Compose the installed shadcn `DropdownMenu`, `DropdownMenuTrigger`, `DropdownMenuContent`, and the appropriate menu item primitives directly at each call site for choice menus, including single-choice form fields, workspace/model selectors, and filters. Use the shared menu primitives' icon gutter and spacing; do not override their internal layout with local CSS. Single-choice and multiple-choice items show the selected state as a check on the right, with text and optional icons aligned to ordinary action items. Keep Radix radio/checkbox semantics; do not add a left radio dot or an extra selection column. See `docs/ux/menu-review-2026-11-01.md` for the agreed convention and audit evidence. Verify each changed menu in the browser, including open state and alignment, before reporting completion.

## Shared UI components

Use the shadcn CLI as the source for standard UI primitives. Use its installed `Button`, `Input`, `Textarea`, `Checkbox`, `Label`, `Dialog`, `DropdownMenu`, `Popover`, `Sidebar`, `Tabs`, `Card`, `Badge`, `Alert`, `Table`, and `Tooltip` components directly at their call sites. Do not hand-build or add wrapper components that duplicate those controls, overlays, navigation, tables, or form primitives; do not create a parallel component library. Do not substitute raw native buttons, text fields, checkboxes, textareas, or data tables where the corresponding shadcn component exists. Keep custom components for Niu-specific behavior, page compositions with no shadcn equivalent, and branded assets. When a needed primitive is missing, install it with the shadcn CLI before considering a custom implementation.

## Dialogs and page simplicity

Follow [the UI consistency standard](docs/ux/ui-consistency-standard.md) for all dashboard pages, dialogs, choice controls, composers, loading states, and visual tokens. Keep management and detail pages as scannable reading and inspection surfaces (tables or concise single-panel key-value summaries) without multi-card sprawl or walls of explanatory prose. Every page-level create, edit, rename, publish, limit-setting, and destructive confirmation action must open an installed shadcn `Dialog` (`DialogHeader`, bounded scrollable body such as `max-h-[90dvh] overflow-y-auto`, and `DialogFooter` with cancellation and primary submit actions, restoring focus to its trigger via `onCloseAutoFocus`). Never replace a read view in place with an inline edit form, embed permanent mutation forms inside a summary page, or expand inline confirmation strips on pages. Conversely, never open a nested `Dialog` inside an already-open modal (such as the global `Settings` dialog); keep secondary flows inside an active modal inline or in-dialog views. Never collapse an open dialog's form or detail frame into a full-body skeleton or raw loading paragraph while fetching choice options or secondary metadata; keep the frame stably mounted and show loading inside the affected control or data region.

## Icons

Use only Lucide React and Tabler Icons for product controls and navigation. Choose icons for their meaning; both libraries are allowed. Keep navigation size, stroke weight and alignment consistent, and use the same icon for the same feature across the sidebar and account menu.

Consider Tabler alongside Lucide when choosing icons. Generations uses Tabler `sparkles`; Chat sessions use Tabler `message-chatbot`; `sparkle-highlight` is another suitable candidate for generative AI actions. Do not limit icon selection to Lucide or add Phosphor or IconPark.

## Workspace terminology

Use **workspace** consistently for Niu's customer-facing scope. Do not call the same Niu entity a **project** in product UI, guidance, or generated setup commands. Keep legacy `project` / `project_id` names only where required by existing API, database, or compatibility contracts; translate them to workspace terminology at the product boundary.

## User-reported issues are global requirements

Treat every defect or UX/engineering complaint raised by the user as a **global product requirement**, never as a one-off local patch. For every user-reported issue:

1. Identify the shared root cause in the underlying UI primitive, base stylesheet, backend contract, or operational workflow.
2. Fix the default behavior so the same class of defect is prevented structurally across the entire product, and sweep the whole repository to clean up every sibling occurrence.
3. Codify the resulting invariant in `AGENTS.md` and [the UI consistency standard](docs/ux/ui-consistency-standard.md), and add an automated regression test (e.g. [PrimitivesConsistency.test.tsx](apps/dashboard/test/ui/PrimitivesConsistency.test.tsx) or Rust integration tests) so future changes cannot reintroduce it.

Standing global invariants established from user feedback:

- **Card-free empty placeholders**: `<Empty>` must stay transparent and card-free (`bg-transparent`, no `bg-card` / `bg-muted` card slabs, no `rounded-[var(--radius-panel)]`, no decorative shadows) across sidebars, drawers, dialogs, embedded sections, and full-width management pages. Narrow rails (such as Generations `Sessions`) use compact padding and an unboxed muted icon (`EmptyMedia` default variant).
- **Default-safe form and dialog field spacing**: `<Label>` must use CJK-safe line height (`leading-snug`, never `leading-none`). Every labeled field in forms, dialogs, and popovers pairs `<Label>` and its control inside an explicit `grid gap-2` (or `space-y-2`) container with uniform label weight and control height, backed by the zero-specificity CSS field-spacing safeguard in `apps/dashboard/app/styles/foundation.css` so text and controls can never overlap by default.
- **Staging post-test data hygiene**: Whenever tests or verification run against staging, clean up all created test customers/organizations, test workspaces, test operators/API keys, and test request/billing debris upon completion while preserving baseline staging configuration (default workspace, staging admin/demo logins, Providers, Vendors, Offers, and Standard Prices).
- **Prerequisite-aware entry points and in-place resolution**: Never route a user into a workspace surface whose required prerequisite is known to be absent (for example, directing a workspace with `active_key_count === 0` from Overview or Models into Playground/Generations without surfacing the missing API key first), and never open an empty selector dropdown as an error response when a required resource is missing. Always guide the user honestly according to their permissions and, when they have write permission, provide a 1-click in-place resolution (such as auto-creating a revocable default `"Playground"` API key with explicit user confirmation) alongside custom setup so they never bounce through dead-end detours.
- **Viewport-appropriate information density over rigid single-column sprawl**: Full-width canvas utilization means never trapping pages inside an artificial centered column — it does NOT mean stretching individual browsable items awkwardly across 1400px–2560px of horizontal space. Browsable item directories (such as the public and workspace Models catalog) MUST render as a responsive multi-column card grid (`repeat(auto-fill, minmax(272px, 1fr))`) so desktop viewports display 3–6 scannable, equal-height cards per row with crisp 3-tier hierarchy (identity + capability tags, clamped summary, pricing/context + action footer), collapsing cleanly to 2 columns on tablet and 1 column on mobile. Every UX review must evaluate real spatial ergonomics, scan density, and viewport fit rather than checking rules mechanically.
- **Unified docs shell and zero unscoped third-party CSS**: Never embed third-party full-viewport SPA widgets with unscoped global stylesheets (such as `@scalar/api-reference-react`) inside the Starlight documentation shell, and never hide `.sidebar-pane` or shift the top header on a documentation subroute. Interactive API debugging belongs natively inside the shared Niu docs shell using installed shadcn primitives (`OperationTryIt` on `/docs/api/rest/<slug>/` pages and `ApiExplorer` on `/docs/api/explorer/`) so styles, navigation, light/dark themes, and `<ClientRouter />` transitions stay 100% cohesive with zero cross-page CSS bleed.
- **Top-bar section tabs replace redundant static page titles**: On top-level single-crumb management pages whose primary view is partitioned by top-level section `<Tabs>` (such as Customers `Customers | Registrations`, Platform Settings, Connection Incidents, standalone Payments, and multi-mode Standard Pricing), render those tabs directly in the top header bar via `<PageHeader tabs={<TabsList variant="line">...</TabsList>} />` (`#dashboard-page-tabs`) instead of stacking a redundant static page title above a second tab strip. Keep the route `<h1>` accessible (`sr-only` when header tabs are active), preserve interactive parent breadcrumbs on workspace/detail pages, and scope nested sub-tabs inside tab content with `<PageHeaderTabsTargetContext.Provider value="">`.
- **Compact dialog controls and explicit zero-price / below-cost safeguards**: Direct-child utility buttons inside `DialogContent` (which uses CSS `grid`) must never stretch full dialog width (`foundation.css` enforces `:where([data-slot="dialog-content"]) > :where([data-slot="button"]:not([data-slot="dialog-close"])) { justify-self: start; width: auto; }`); place dialog refresh actions as compact header icon buttons and pagination/close actions in `<DialogFooter>`. Always label admin publication notes (`Publication note:` / `发布备注：`) instead of rendering unlabeled floating strings above pricing tables, surface `below_cost` / `$0.00` (free) alerts directly inside price history dialogs, and require explicit confirmation before publishing a `$0.00` customer text rate.
- **Explicit Provider supply readiness on Standard Pricing**: Saved commercial standard prices persist independently of Provider enablement, so Standard Pricing MUST surface live commercial supply readiness (`active` with active Provider names, `inactive` when routes/credentials/offers are disabled, or `unconfigured` when no route exists), sort active-supply models first, provide a shadcn `DropdownMenu` supply-status filter, and never mask unsupplied historical prices behind a vague `"Comparison unavailable"` label.
- **Unified two-tab Provider detail (`Configuration | Analytics`), default-all model access, and zero Provider member UI**: Upstream Providers are platform-managed vendor connections — Providers inspect usage on their own vendor consoles, never by logging into a customer's Niu installation. Provider detail (`/admin/providers/:provider`) exposes strictly two tabs: **Configuration** (`配置`, consolidating profile + default integration, API keys, and model access/discount policy onto one scannable page) and **Analytics** (`统计`, consolidating 90-day model/media usage, payables, and settlements). Never expose a Provider `Members` tab, member-assignment dialog, or member-referencing deletion copy, and never dump the entire 300-row model catalog onto the Configuration page by default: default to **All models** with **no discount (`100%`)**, list models inline only when **Allowlist** or **Blocklist** is active, and place full catalog inspection inside the bounded **Browse models** dialog (with in-dialog subviews, never nested `<Dialog>`s).
- **Distinguish unconfigured (`Pending setup` / `待配置`) from disabled (`Disabled` / `已停用`) across all resource states**: Never label an unconfigured resource (such as a Provider with zero stored API key credentials `configured_api_keys === 0` or an erased connection `!has_credential`, zero imported models, or unconfigured model pricing) as `"disabled"` or `"not enabled"` (`未启用` / `已停用`). Surface missing setup explicitly as **Pending setup** (`待配置`) with the concrete missing prerequisite (**API key not configured** / `API 密钥未配置`, **No models imported yet** / `尚未导入模型`, **Model pricing not configured** / `模型价格未配置`), reserving **disabled** (`已停用`) strictly for resources that already hold saved configuration and were explicitly turned off.
- **Unmistakable `aria-pressed="true"` active state on choice/preset/toggle buttons**: Never distinguish selected vs. unselected choice/preset buttons solely by swapping `variant="secondary"` against `variant="outline"` (whose backgrounds collapse in dark mode and leave the selected option borderless and dimmer than unselected items). Always express choice/toggle selection with `aria-pressed={selected}` on shared `<Button>` controls, backed by the `--choice-active-bg` / `--choice-active-fg` / `--choice-active-border` brand-tinted selection tokens in `apps/dashboard/app/styles/foundation.css` and `apps/dashboard/app/components/ui/button.tsx` so active selections stand out unmistakably in both light and dark themes.
- **Reserve `Not published` (`未发布`) strictly for unpublished commercial availability — never stamp `Capabilities not published` (`能力未发布`) on callable model cards**: When an upstream OpenAI-compatible `/v1/models` endpoint omits optional modality metadata (`output_modalities`), never label a callable model card as `"Capabilities not published"` (`能力未发布`), which is redundant jargon that misleads users into thinking an active model itself is unpublished while offering `Try in Chat`. Keep callable model card footers clean when optional modality tags are absent, state missing upstream modality declarations plainly on the detail page without `"published"` terminology, and use concise **`Not published`** (`未发布`) exclusively on genuinely uncallable commercial models (`callable === false`, which never expose trial actions).

## UX review delivery gate

For substantial new or changed user-facing workflows and actionable UX feedback, use the `ux-review` skill when available and complete its review before delivery. If the skill is unavailable, apply the requirements below directly; do not block on installation. Respect explicit review-only requests.

Review the complete user task and affected sibling surfaces: discoverability, configuration scope, terminology, input choices, loading, missing configuration, failures, permissions, save feedback, revisit and recovery. Place settings according to their scope; use recognizable choices instead of requiring users to recall internal codes. Keep persisted values separate from presentation and preserve historical data semantics. Fix shared causes and update dependent guidance and links together.

Implement and verify authorized corrections rather than ending with an acknowledgment, plan or list of recommendations. Inspect actual mature-product references and the final rendered desktop and narrow layouts, including changed menus/dialogs and keyboard interactions. Passing tests or a closed-state screenshot alone is insufficient. Do not report completion with a known major usability defect in the affected journey; continue fixing or identify the concrete blocker and unverified behavior. Do not expand this gate into unrelated redesign work or add unnecessary approval steps.

UX judgments must cite applicable rules from the skill's source-backed standards, with concrete pass/fail evidence. Functional correctness does not establish visual quality: separately inspect hierarchy, grouping, spacing, action emphasis and content density. Check intermediate desktop and split-pane widths with navigation both open and closed; measure actual content width and accumulated wrapper gutters rather than only checking phone overflow. Distinguish published requirements, design-system recommendations and Niu-specific constraints. Keep Admin Settings as the final sidebar item.

## UI change verification

For every UI change, run the product and inspect the rendered result in a browser at the affected route. Review both the visual hierarchy and the relevant interaction states; check a narrow viewport when the layout is responsive. Fix clipping, overflow, spacing, alignment, contrast, and inconsistent components before considering the change complete. A passing build or test suite alone does not verify UI work.

## Reference-led UI design

Implement visual changes directly with the installed shadcn primitives, existing Niu brand tokens, and inspected mature-product references. Verify the rendered result and interaction states in the browser. Do not introduce a mandatory external design-generation step or treat mock data and unsupported capabilities as product requirements.

This is mandatory for every UI task: do not invent a new UX pattern or visual layout. Borrow an existing, proven pattern from a mature product. For features comparable to OpenRouter, use OpenRouter as the default reference unless the user names another product. Inspect the actual relevant page and interaction states before editing; do not work from memory or call a loosely inspired redesign a faithful implementation.

Follow established patterns from mature products rather than inventing layouts based on personal design judgment. When the user supplies a product or page to copy, inspect the actual reference before implementation and treat its page structure, visual hierarchy, spacing, and interactions as requirements, not loose inspiration. Preserve Niu's brand tokens, shared components, and established navigation shell around the referenced content layout. Reuse existing components before introducing custom ones. Do not fabricate data or capabilities to imitate a reference.

Before delivery, compare the rendered result directly against both the reference and equivalent Niu pages at desktop and narrow widths. Fix visible deviations and inconsistencies within the authorized scope; do not merely describe them or wait for the user to point them out. If a departure is required by a concrete product or technical constraint, explain that constraint rather than silently substituting a new design. When no reference is supplied, inspect a relevant established product pattern before choosing a new layout.

## Navigation hierarchy

Use a single left sidebar for primary navigation; do not add a separate outer product rail alongside the sidebar. Keep the brand mark and workspace switcher in the sidebar header, primary destinations in the main sidebar list, and Docs, Admin access (when authorized), and the account menu in the sidebar footer. For a feature that needs two navigation levels, use sidebar items for the first-level sections and tabs within the selected section for the second level. Tuck secondary, low-frequency, or scenario-specific capabilities into their parent feature's tabs or advanced sections rather than promoting them to top-level sidebar items. Use the installed shadcn Sidebar and Tabs primitives directly, preserve clear active states, and verify the hierarchy and access to both levels at narrow widths.

## Surface styling

Dashboard management pages use the full available content width between navigation and canvas padding. Never add a fixed page width, centered bounded canvas, or page-level max-width. Only the Generations chat reading column may retain a readable maximum width. Dialogs and individual form controls may use appropriate bounded widths. Apply this rule to design briefs and the shared design system.

Model lists use a directly visible filter field in the first toolbar row, alongside list actions; they are exempt from the secondary-search popover rule. Search is a secondary action outside Logs. Show a compact search icon that opens an installed shadcn Popover search panel; do not leave large search fields permanently visible in page or sidebar layouts. Keep active filters apparent on the trigger, preserve the query when closing, and support keyboard focus and dismissal. Logs may retain a directly visible search field. Search fields inside an already opened choice menu or dialog remain appropriate.

Use Manus as the reference for the shared visual treatment of agent-product surfaces. Prefer subtle solid background tones and spacing to separate navigation, content, and sections. Avoid repeated bordered cards and decorative shadows. Reserve elevation for floating panels, menus, and dialogs; retain meaningful input, focus, selection, and data-table affordances. Preserve Niu branding and use shared theme rules rather than page-by-page overrides.

## Status and list information

Design management lists around the decision users need to make. Every column and status must distinguish meaningful outcomes or support a concrete action. Do not expose a backend field merely because it exists, or display universal labels such as “Configuration saved” on lists containing only saved records.

Keep API credential presence, configuration, current Provider and offer qualification, supply readiness, live upstream verification, and workspace selling eligibility distinct. An API key or enabled route does not establish sellable inventory. Derive supply readiness from current approved, active model/rate offers and their matching enabled routes and credentials. Customer selling prices and authorization remain workspace-specific. Show missing requirements and link to the relevant remedy; never infer a positive state when evidence is unavailable.

## Provider terminology

Use **Provider** consistently for model-supply businesses, upstream API services/adapters, offers, memberships, earnings and settlements. Preserve existing API, route and storage contracts, including legacy supplier-named identifiers.

## Internal identifiers

Never display internal GUIDs/UUIDs in product UI, including shortened IDs, secondary labels, tooltips, menus, dialogs, and raw-data panels. Use meaningful names, dates, or user-facing references instead. Keep internal identifiers in API contracts, routing, storage, and diagnostic logs; they are not user-facing content. Do not substitute an ID when a display name is missing.

## Readable product URLs

Use durable, human-readable slugs for named product resources in browser paths and query scopes, including workspaces, Providers, and API key detail pages. Call the public field `slug`. Generate suggestions from names, normalize whitespace and punctuation, and transliterate Chinese to lowercase pinyin without tones. Preserve user edits, handle collisions, and keep saved slugs stable across display-name changes. Keep UUIDs in existing API, authorization, and storage contracts; preserve old bookmarks with authorized resolution and canonical redirects. Do not derive a URL from private prompt content. See `docs/reference/readable-product-urls.md` for the route audit and remaining record-reference migration.

## Durable product data

The backend is the source of truth for saved product data, including Chat sessions, messages, responses, settings, and attachments. Browser storage may only be a disposable cache. Clearing it or using another browser must not lose saved data. Never replace backend persistence with browser-only storage as a shortcut.

## Commercial data boundaries

Provider purchase prices, upstream expenses, procurement budgets, and platform margins are confidential platform information. Never show them in customer workspace pages, Chat, Observability, usage reports, exports, or customer API responses. Customer billing and request costs mean customer-facing charges only; never substitute supplier cost when a customer charge is unavailable. Keep procurement controls in platform administration, and restrict providers to their own agreed rates and settlements. Enforce these boundaries in backend authorization and response serialization, not merely by hiding UI elements. Installation administrator access does not justify mixing procurement information into customer-facing workspace screens.

Zero-key generation sessions must disable the prompt, attachments, starter prompts and all submission paths. Keep prior drafts readable. Confirm key creation separately from sending a request. Aggregate duplicate empty notices for one collection and keep the recovery action beside the empty result. See the UI consistency standard.

Model mapping dialogs show a single title, the editable mapping fields and visible Cancel and Save actions. Keep catalog metadata and optional capabilities under advanced settings. Show video configuration for declared video output, unknown output, or an existing saved video configuration.
