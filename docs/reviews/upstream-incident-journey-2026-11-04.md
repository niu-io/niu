## Deterministic recovery-boundary verification — 2026-11-06

Follow-up for `niu-ya50.1.1` against handoff commit `a57b1dc528e0125adaa9e9cbe300a3b6e79002e9` plus the receiving working tree (product migrations 0412–0417 unchanged by this increment), run in a disposable PostgreSQL 17 cluster through `scripts/test-postgres.py`. The tests write attempt routing, failure, timing and execution evidence directly. They perform no upstream transport, Provider call, real gateway request, browser session or hosted deployment operation. This is deterministic storage evidence, not live recovery acceptance.

```sh
for test in account_restriction_is_durable_without_claiming_nonexecution \
  recovery_requires_current_connection_and_model_revisions \
  pending_mapping_change_serializes_against_recovery \
  concurrent_failure_observation_blocks_recovery \
  newer_failure_or_incident_requires_later_current_success; do
  python3 scripts/test-postgres.py "$test" --package niu-storage --test provider_incident_evidence
done
```

Result on 2026-11-06: each invocation `1 passed; 0 failed`. The disposable cluster is sized for one migration application at a time: running all five tests in parallel in one invocation exhausts its default shared lock table during concurrent migration setup. That harness limit is why the evidence command runs one test per fresh cluster; it does not indicate a product failure.

- The existing restriction test still proves deduplication, retained `may_have_executed` classification and that late success evidence does not mark the restricted attempt nonexecuted.
- `recovery_requires_current_connection_and_model_revisions` records a restriction, dispatches two candidates under the original connection and model revisions, advances the connection revision with `Store::update_vendor`, retargets the same alias with `Store::upsert_vendor_model` and its expected revision, then completes the candidates with timing-first and execution-first evidence. The incident stays active with one observation, stored observation revisions remain the failure-time revisions, and a later success bound to both current revisions resolves it. A subsequent incident cannot be resolved by a success while the connection is disabled; re-enabling requires a success bound to the re-enabled revision. Execution alone and an incomplete 2xx timing do not resolve.
- `pending_mapping_change_serializes_against_recovery` holds the same `vendor_models` row update as `upsert_vendor_model` (new upstream target and revision+1) uncommitted while complete successful timing and the execution transition arrive. The recovery query waits on the row lock, re-evaluates after the commit and does not resolve the incident; a success dispatched after the committed change resolves it. This covers a concurrent connection-or-mapping change.
- `concurrent_failure_observation_blocks_recovery` holds the recorder's newer-observation row update on the active incident uncommitted while complete successful timing and the execution transition arrive. The recovery update waits on the incident row, re-evaluates after the commit and does not resolve; the observation count stays two, and a success dispatched after the observation resolves it.
- `newer_failure_or_incident_requires_later_current_success` exercises both evidence arrival orders. A success dispatched before a newer failure cannot clear the newer observation, and late success evidence for an attempt dispatched before a newer incident cannot clear that incident. Only a success dispatched after the newer evidence resolves it. The failure attempts stay `may_have_executed` with `unknown` usage confidence, the restriction row is retained, and no cost or customer-balance reservation is created.

Binding implemented in the reviewed source:

- `connection_incident_observations.model_revision` (migration 0414) preserves the effective model mapping revision observed at failure time. Existing rows are backfilled from the attempt's managed route, are `NOT NULL` and positive, and recovery never rewrites them.
- The resolver joins the recovery attempt's dispatch-time `managed_attempt_routes` revisions to the currently enabled `vendors` and `vendor_models` rows for the same connection and alias, excludes attempts with any `request_failures`, requires `confirmed_completed` execution plus complete 2xx timing, and requires the incident's latest observation to precede the attempt dispatch. An incident observation taken under a newer connection or model revision than the success also blocks resolution.
- Migration 0415 adds `FOR SHARE OF v,m` to the resolver, so a concurrent mapping or connection write cannot commit between the revision check and `resolved_at`. The resolver waits and re-evaluates under READ COMMITTED; only a later success bound to the new revisions resolves.
