# Key lifecycle and organization boundaries — 2026-11-05

Tracking: `niu-ya50.2.2`, `niu-ya50.3`, `niu-z2r`, and `niu-287.32`. These findings remain open for their broader acceptance criteria. The checks below used a fresh isolated resale-mode PostgreSQL database, local gateway and browser. The only balance was an isolated noncash customer grant, not a payment or a Provider procurement budget; no real upstream request or external notification was sent.

## Concurrent and browser key lifecycle

At source revision `cace2f4a`, concurrent real HTTP rotation requests using the same idempotency key returned 201 and 200 for the same replacement, with a secret in one response. Different idempotency keys produced 201 and 409. In a separate rotation-versus-revocation race, revocation won (204 versus 409). Independent database reads found respectively one, one and zero live descendants; all original tokens returned 401. Surviving management-only replacements exposed only the two approved read capabilities. These are observations of three schedules, not a proof of all possible interleavings.

A browser then rotated an invocation-disabled management key. Before the correction the one-time-secret dialog offered Generations and registered it as a chat key. Administrative key views now include the already persisted `invocation_allowed` flag, and the dialog presents invocation guidance and chat registration only when that flag is explicitly true. False displays the management-only restriction; an absent flag is treated as unknown. The corrected browser flow rotated an unfunded management key, showed the management-only message without a Generations link, and revoked its replacement; independent HTTP checks found the original and the revoked replacement rejected. An invocation-enabled key in the funded test organization retained the Generations action. No inference was sent.

Before the correction, a no-funding create rejection left an ambiguous recovery record that blocked subsequent rotations. The payment-readiness middleware returns its structured refusal before invoking the mutation handler. The browser now recognizes only that exact 503 type and one of its documented readiness codes as a confirmed rejection; ordinary server and transport errors still retain the request identity. In the actual browser, an unfunded create returned to the editable form with the readiness message, and a management key could subsequently be rotated. An isolated gateway interruption produced 502 and preserved the recovery dialog; retry after the gateway restarted returned the explicit readiness rejection and exited recovery. This does not establish behavior for every intermediary, generic 503, delayed response, or browser-storage loss.

The existing secret dialog and shared controls were retained. Its management-only state was visually inspected at desktop and 390 CSS pixels with the displayed secret masked for screenshots, and the ordinary state was operated. The state distinguishes authorization from model scope and follows [WCAG 2.2 status messages](https://www.w3.org/TR/WCAG22/#status-messages) and [reflow](https://www.w3.org/TR/WCAG22/#reflow); this is not a full accessibility review. OpenRouter's actual key settings led to a sign-in wall, so its authenticated interaction was not compared. No new layout was introduced.

## Organization, workspace and customer billing

The browser created a sibling workspace in the original organization and another organization, then switched between them. Credits showed the original organization's synthetic $1.00 customer grant in both of its workspaces and $0.00 for the other organization. A separate owner scoped only to the first organization obtained its own balance (200), received 404 for the other organization, and received 401 for both after that operator was revoked. A separate workspace-scoped viewer signed into the actual browser with its own access token; after that isolated operator was revoked, reloading the key page returned the browser to sign-in. This does not establish every role transition or a complete invitation journey.

The second, unfunded organization's workspace billing page initially returned a payment-readiness error. Only the registered GET routes for customer billing overview and invoice history/detail now bypass that readiness gate; their existing workspace authorization remains in force. Afterward actual HTTP checks returned 200 for the authorized empty overview and invoice history, 404 for an unauthorized organization, 401 anonymously and after member revocation, and 503 for an invoice POST in the unfunded workspace. The browser displayed the workspace's empty spending and statements. This does not establish populated invoice-line isolation or real settlement, nor does it authorize changes to customer billing or Provider purchase costs.
