# Staging UX acceptance test requirements

Tracking: `niu-287`. Use [the user stories](staging-user-stories-2026-11-02.md) as the scenario inventory and Beads as the source of current work and acceptance state. This document specifies how to test; it does not certify that any story passes.

## Test execution

- Test the deployed revision and record the deployment version, commit, operating mode, test date, environment and test account roles. Compare the deployed revision to the revision containing each fix before evaluating it.
- Start each story from its realistic entry point with both empty and populated data. Exercise the complete task through success, read back the saved result, refresh, and revisit it in a separate browser session where persistence matters.
- Initially review at a consistent wide desktop viewport. Test intermediate and narrow layouts, including open and closed navigation, together in the later responsive pass requested by the product owner; do not mark responsive acceptance as passed before that pass.
- For each story and branch record pass, fail, blocked or untested, observable evidence, role and scope, and the corresponding Beads issue. A passing screenshot or unit test does not establish end-to-end success. Recheck failures against the current revision and update existing issues instead of duplicating them.
- Inspect visual hierarchy, grouping, spacing, density and action emphasis separately from functional behavior. Exercise focus, keyboard navigation and dismissal on changed interactive controls, and review both English and Simplified Chinese.
- Use dedicated test organizations and workspace data. Do not record credentials, sensitive prompts, private provider responses or confidential financial data in evidence or issue descriptions. Only perform paid operations with an explicitly authorized funding source and known limits.

## Required journeys and branches

1. **Discovery and access (S01–S02a):** Public catalog with real data, no data and service failure; documentation and installation availability; login success, invalid credentials, unavailable login methods, expired session and destination restoration. Verify initial installation and administrator access separately from an ordinary user session.
2. **Provider to first usable model (S03–S04, S20):** In both internal and resale modes, connect a supported preset using only an API key, verify automatic discovery and route availability, and complete a real first request when authorized. Test an invalid or restricted key, unavailable discovery, empty catalog, interrupted connection, retry, credential rotation and re-import without duplicate or overwritten user settings. A saved credential must never be presented as proof of successful verification or sellable inventory. Test resale offer, authorization and customer pricing independently.
3. **Models and agent onboarding (S05–S06a):** Follow catalog discovery through workspace access, setup, agent authorization and readback. Verify missing models, denied access, expired or declined authorization, unavailable installation artifacts and recovery. Check that deployment and workspace scope in setup guidance match the actual environment.

   In the normal approval page, model calls start disabled. Enabling them requires choosing fixed model names from the reviewed workspace, and any scope/selection change invalidates consent. Verify individual choice, select-all-current without wildcard, filtering/no matches, arrow-key entry from the filter, Enter selection and Escape dismissal. The primary surface shows only workspace, invocation, model scope, one-hour duration and the spending boundary; task context, interface narrowing, management detail, spending basis and expansion policy appear only under Advanced options. Verify a requested task is shown as self-reported context, narrowing interfaces resets consent, and an empty interface set blocks approval with an actionable message. Failed, malformed and empty catalogs must prevent invocation approval while allowing a deliberate return to management-only access. Verify organization identity alongside workspace. After actual approval and exchange, add a configured model: an owner can discover it, but the earlier named key cannot discover or invoke it. Check actual `allowed_models`, `invocation_allowed` and `invocation_protocols` readback; do not infer authority from a successful login. Confirm an interface omitted from the grant receives the dedicated 403 while an approved interface reaches the normal model/admission checks. Preserve historical wildcard semantics. A customer-charge limit must never be described as a cap on owner-funded upstream expense, and a conversationally agreed budget must not be described as enforcement.

   Include a Provider that distributes third-party models, an unknown model identifier and a direct model. Check the public catalog, workspace filters and model details: Provider identity and model developer are distinct, inferred developer names are labeled as unverified, and unknown names are not invented. Check agent-facing metadata separately against its documented provenance.
4. **Chat, video and assets (S07–S08c):** Start a new conversation and video task as a signed-in user, select an accessible model, send, observe completion, reload and recover saved history. Verify no unnecessary key-secret entry, clear payment information outside the composer, in-flight and failed states, unsupported capabilities, authorization denial, budget exhaustion, idempotent video submission and no accidental duplicate charges. Test asset access, deletion effects and consent only where supported and authorized.
5. **Workspace governance (S09–S10a, S18–S19):** Create, inspect, update and revert supported pools, evaluations, guardrails and subscriptions; validate navigation, authorization, conflict handling and saved state. Verify that agent changes remain within delegated authority and that unsupported capabilities are labeled accurately.

   Find routing, evaluations and event subscriptions directly from the workspace navigation, then open a detail and return to its list without leaving the selected workspace. Check active navigation and preserved existing links for an ordinary member as well as an administrator.

   In platform routing, configure more than twelve Provider connections and confirm models from the last connection can be selected. Exercise a lost response after both successful and unsuccessful writes: the editor must retain the draft, prevent unsafe duplicate writes, and let the administrator reconcile the authoritative saved state before safely continuing. Check discovery failures, conditional rules, revision conflicts and history without relying on internal revision numbers.
6. **Organizations and workspaces (S11–S13):** Create an organization, invite or manage members where supported, switch organizations and create or select workspaces. Verify owner, administrator and viewer permissions, stale sessions and removed members; ensure switching never displays or modifies another organization's resources. Check that infrequent organization administration does not dominate the account menu.

   Before any platform currency, merchant or company funding exists, verify organization member management can resolve workspace names through both supported directory API aliases. Authorized owners can list their organization's workspaces; foreign-organization and ordinary inference credentials remain denied. Verify the three non-inference Routing/Evaluations/Event subscriptions destinations through normal browser navigation and delegated API access. Save and reopen configuration, test stale revisions and cross-workspace access, then attempt inference separately: reaching configuration must never imply authorization or funding for execution. Repeat with payment readiness temporarily unavailable to verify management remains usable without inventing a healthy billing state.
7. **Billing, usage and logs (S14–S17):** Verify funding source, balance, workspace and key limits, customer-facing price, usage and billing evidence in internal and resale modes. Check insufficient funds, zero and unlimited budgets, denied operations, failed requests and history. Customer surfaces and responses must not reveal Provider purchase prices, upstream expenses or margins. Reconcile charges only against actual authoritative records.
8. **Administration, localization and recovery (S21–S23a):** Verify installation-level access and scope separately from organization administration, customer isolation, payment and branding settings, and audit evidence. Check current version in About after release, saved data after storage clearing or a new browser, legacy links, missing resources and destructive-action scope. Do not claim the future Provider portal is available without deployment evidence.

For standard text and media price publication, leave the optional note empty and verify the saved price, immutable actor audit and an idempotent retry after a lost response. Verify a supplied note is preserved, while actions that still require an explanation reject an empty one. Exercise closing and returning to an uncertain publication without losing its retry identity; compare historic media rates to ensure existing precision and rounding are unchanged.

For customer setup, inject both definitive validation failures and lost responses after server-side creation for company, workspace and owner. Verify fields remain editable, an unchanged retry uses the original idempotency key, edited details are never silently sent as the old request, and a new request uses a new key only after the duplicate-risk warning. Reopen the dialog and verify recovery. For password setup, test rejected input separately from an uncertain save, and verify revision checks and session revocation without recording a password.

## Release evidence and handoff

Run appropriate automated tests and build checks for changed code, then verify the actual rendered workflows and relevant error states in the deployed environment. Record which operations were simulated, which contacted a real Provider and whether any paid request was made. Link failures and remaining unverified cases to Beads; keep issues open until their full acceptance scope is supported by evidence. Deliver the story-by-story results to the designated reviewer together with the deployed revision and known limitations.
