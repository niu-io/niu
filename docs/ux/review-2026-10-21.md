## Intent and task model before current navigation

Authority: [product focus](../product/product-focus.md), user-confirmed pricing/payment clarifications in [blueprint](blueprint.md), and current repository instructions. Niu helps operators run a model delivery business; customers need usable access, predictable charges and retrievable results. User tasks, not API resources, determine the proposed homes below. These groupings are review proposals, not approved redesigns.

| Operator | Make a model reliably available | Provider connection, offered models, routing and readiness | Model supply, with related Provider and routing views | Upstream APIs and model names; not Niu adapter internals |

| Customer creator | Generate, revisit and reuse an output | Sessions, outputs and supporting media assets | Generations with contextual output/material management | Prompt, model and output; not Provider module or task bindings |
| Customer/operator | Understand usage or diagnose a failed request | Scoped analytics and individual request evidence | Activity with drill-down to Logs | Usage and request errors; not an internal execution schema |

Alternative to current structure: organize by the above responsibilities, nesting secondary record views under their task owner. Retain specialist views where actor, scope or frequency justifies them; do not merge everything into a single page. Evaluate that alternative against current UI, permissions and discoverability below.

## New findings

### UX-22 — Account funding has no coherent task home

**P1 · structure/journey · high confidence in observed split; user effort is expert inference.** R02; C1/C2/C4.

The account balance is in Settings → Billing, adding money is in Settings → Payments, and workspace Billing shows spending/limits without a funding handoff. The account balance view has no direct Add funds action. A customer approaching a low balance must infer the relationship among three similarly named destinations. Changing their headings alone leaves that path fragmented.

Propose one account Billing home for balance, funding, payment history and charge activity; retain clearly scoped workspace spending and limits with a direct account-funding link. The same balance may legitimately appear near checkout: repetition serving a decision is not the defect. Retain distinct payment/order/ledger records and access controls underneath.

Acceptance: from workspace spending, a low-balance notice or account balance, the owner can identify whose funds are shared, add funds, understand pending/failed payment and return to the original task. A member lacking funding permission gets the proper owner handoff. Compare this with actual users using goal prompts that do not name pages.

### UX-23 — Model setup is partitioned around credentials and purchase records

**P1 · structure/operator workflow · high confidence in navigation; medium in proposed grouping.** R03; C1/C2.

Provider Overview's model-configuration step leads into API keys. The Models section describes purchase offers, while route configuration is reached through a credential's Model routes dialog. Making one model available requires understanding this internal distinction before the product establishes a coherent model-level view.

Propose a model-centered supply workflow that connects upstream model/alias, credential assignment, offer and commercial readiness. Keep connection secrets in credential management and preserve the distinction between personal availability and commercial eligibility. A pool is a legitimate advanced routing specialization, not automatically an unnecessary page.

Acceptance: an operator given “make this model usable for the intended audience” can discover each missing prerequisite and its remedy from model context, without being told the internal location of route mappings. Verify changing credentials, absent offers and personal-only use; preserve all authorization/compatibility contracts.

### UX-24 — Publishing media prices requires undocumented internal dimensions

**P1 · input/knowledge boundary · high confidence.** R04; C2. Source: `features/retail-pricing/media-editor.tsx`.

The form asks for free-text Channel, Resolution and Billing meter, plus Decimal scale and half-even rounding policy. Its model menu can show no registered shared models without an actionable configuration handoff. The form explains storage and enrollment limitations instead of establishing how an operator chooses valid billing dimensions. Knowing how to set a commercial rate does not imply knowing Niu's matching codes or exact-number representation.

Propose supported specification choices derived from the selected model, recognizable billing units, sensible policy defaults and a calculated price example. Expose advanced precision only where a real user task requires it. Do not fabricate supported model options; unavailable configuration needs an explicit remedy. This is additional to UX-02's placement issue: moving the current form does not repair its knowledge burden.

Acceptance: publish a valid text and media tariff from actual supported capabilities without looking up source/schema codes; unsupported combinations are prevented or explained before submission. Confirm persisted precision, historical rates and billing behavior remain correct.

### UX-25 — First-request guidance conflates installation operator and customer developer

**P2 · role/handoff/documentation · high confidence.** R10; C1/C2.

Rendered Quickstart tells the reader to start Niu and connect a Provider before creating a workspace key and making a request. These are separate roles in the intended commercial product. A customer should not need upstream credentials or installation access to consume an already configured service. An operator still needs a complete setup guide.

Propose distinct “operate Niu” and “use your workspace API” paths with explicit prerequisite ownership and links. Preserve shared client examples instead of duplicating incompatible instructions. This is broader than UX-12's stale-setting guidance: it changes who the instructions address.

Acceptance: a non-admin customer can identify their starting point and complete access/client setup using only their permissions; missing service readiness directs them to the responsible operator. The operator path separately covers supply, pricing and valid payment setup before customer access.

## Visual and interaction assessment

Visual quality was assessed separately from task completion. Current payment cards make enabled/disabled/unconfigured states and mock cost warnings visible; key creation has progressive limits; account currency is at platform scope; Settings is the final Admin item. These are useful corrections, not proof of overall readiness.

At **1100px** with navigation expanded, the sidebar occupies 256px after the 68px product rail, leaving 776px main width and approximately 23.28px gutters per side. Collapsing navigation leaves 1032px main width with approximately 30.96px gutters. At **390px**, the page width and scroll width both measure 390px and the sampled pools canvas has 16px gutters. Its toolbar wraps and the creation action remains reachable. The earlier excessive-padding screenshot is not a current reproduced defect.

At **900px**, administrative tables can require horizontal scrolling; account balances places later actions outside the initial view. This is a follow-up usability risk, not an automatic failure: verify identity/action persistence with representative long records before prescribing a replacement layout. Provider routes, media pricing, funds dialogs, catalog, generation history and logs were visually sampled. The media form's dense implementation explanation competes with the actual decision inputs; UX-24 addresses the cause before typography.

The funds method menu and nested dialog dismissal were checked, including return of focus. No comprehensive keyboard, screen-reader, contrast, alternate-theme or every-dialog qualification was performed. A clean narrow empty state cannot certify all populated states.

## Repair dependencies and product conclusion

1. Reconcile the commercial model and actor ownership: platform prices, independent customer account, valid global payment prerequisite. Preserve the user-confirmed direction; determine migration effects before removing contracts.
2. Establish complete operator supply/pricing and customer funding/access paths. UX-22/23/24/25 describe gaps that isolated copy or card redesigns will not repair.
3. Connect generation prerequisites, retained results, request diagnosis and modality-aware financial consumers; retest historical data/state defects with appropriate fixtures.
4. Re-run role-based task walkthroughs and visual/keyboard checks against the resulting structure, then polish local presentation.

**Niu is not established as self-service ready.** Current privileged, read-only evidence demonstrates useful existing screens and saved-result access, but the commercial journey still requires unexplained role and page transitions. This initial pass was incomplete; see the continuation for the completed bounded evidence ledger. It was not exhaustive discovery, independent usability research, end-to-end payment qualification or a release sign-off.

Remaining verification needs: restricted customer/Provider actors; new-customer onboarding; absent/invalid payment setup; successful/pending/failed payment outcomes; real price publication and metered use; media earnings; rich-result variants; dirty cross-section saves; retention/recovery; alternate themes and assistive technology. These require controlled fixtures or authorized consequential actions, and must not be converted to passes because page inspection is complete.
