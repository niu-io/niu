# User stories for the staging UX review

Review tracker: `niu-287`. Prepared 2026-11-02 after initial staging inspection and expanded 2026-11-03; this model is informed by that inspection and is not a blind assessment or a newly approved product specification. Use these stories to guide the review, not as a claim that every capability is implemented. Evidence and findings are in [the staging review](staging-review-2026-11-02.md) and [the workspace IA & UX review](workspace-and-ux-review-2026-11-02.md); current work is in Beads.

## Purpose, actors and assumptions

Niu is **The Model Platform for Agents**: people set goals, authority and budgets; agents discover, evaluate and manage models within those bounds. Niu provides trustworthy information, authorized controls and verifiable results. Agent task completion and quality/cost tradeoff decisions remain the agent's responsibility. Sources: [product principles](../product/agent-oriented-principles.md), [experience blueprint](../product/agent-experience-blueprint.md), [product focus](../product/product-focus.md), [Provider onboarding](../product/provider-onboarding.md), [workflow delivery plan](../product/workflow-delivery-plan.md), and the user's 2026-11-02 direction:

- Provider presets should need only an API key for standard onboarding, with model discovery and configuration handled by Niu; the product must absorb protocol/routing complexity instead of exposing internal CRUD.
- A saved key does not prove successful upstream authentication, catalog availability or entitlement to every model. Unknowns stay unknown.
- Self-service multi-organization creation and an unobtrusive account-menu organization switcher are part of the target experience (confirm deployed revision against `niu-r2k` before treating staging behavior as current source).

The older [blueprint](blueprint.md) reflects earlier operator-first and payment-gate assumptions. Current product principles and subsequent user decisions supersede those conflicting assumptions; older evidence remains historical.

### Actors, authority boundaries and operating modes

A single person may hold several roles across scopes, but the UI and backend must keep their authorities distinct:

| Actor | Scope and primary surfaces | Allowed authority | Explicit boundary |
| --- | --- | --- | --- |
| **Public visitor** | Public landing, `/models`, `/docs` | Browse public catalog, read orientation and agent onboarding prompts | Catalog presence does not grant model access or prove live upstream capability. |
| **Account holder (new or returning)** | `/login`, `/connect`, global `SettingsDialog` (`Account`, `Appearance`, `About`), organization switcher | Authenticate, recover access, approve/decline agent device handoffs, create or switch organizations | Signing in does not grant installation administration or another organization's data. |
| **Organization owner / admin** | `/workspaces`, global `SettingsDialog` (`Billing`, `Payments`, `Members`) | Create workspaces, manage organization members/roles, view shared balance/transactions, top up funds, set low-balance warnings | Organization administration does not expose platform procurement rates, supplier agreements or installation settings. |
| **Workspace member (`Admin` / `Viewer`) or developer** | `/workspaces/:workspace/*`, `/generations`, `/activity` | `Admin`: manage workspace API keys, spending limits, guardrails, assets and workspace settings. `Viewer`: read-only inspection of workspace resources, evaluations, pools, logs and history | Workspace membership never grants organization-wide billing mutation, cross-workspace access or platform `Admin` rights. Revoking an organization-wide member inside a workspace view must not happen silently without clear organization scope. |
| **Coding agent** (via MCP, native host plugin or scoped API key) | MCP tools/resources, `/connect` device flow, `/v1/*` gateway & management contracts | Discover capabilities/prices, run bounded evaluations, propose or apply authorized pool/policy/subscription changes, invoke inference/media jobs, read back state and request evidence | Cannot elevate a workspace key into administrator authority, silently change billing sources, or bypass human review on ungranted mutations. |
| **Platform installation operator** | `/installation`, `/admin/*` (`Providers`, `Routing`, `Pricing`, `Customers`, `Balances`, `Payments`, `Branding`, `Settings`, `Audit`) | Configure Provider presets/keys, import private or commercial routes, qualify offers, publish customer prices, manage payment gateways, credit limits, branding and support | Installation access is additive and must not leak confidential procurement costs, upstream expenses or margins into customer-facing workspace views or APIs. |
| **Provider representative (future / unverified)** | `/providers/:provider/:section?` (where enabled) | Target: inspect own business profile, agreed offers/rates, usage and settlement states | Cannot connect platform credentials, view other Providers, or see platform retail margins. Current admin-mode evidence says Provider is not a supported login role and Provider financial tasks are performed by administrators; do not describe self-service as shipped. |

### Operating and funding modes

Every story involving model access, pricing or billing must be evaluated against the deployment's operating mode (`NIU_OPERATING_MODE`):

1. **Internal use (`internal`, default):** The owning account supplies the upstream Provider API key and pays the upstream Provider directly. Niu manages discovery, private model import, routing, model pools, and usage/expense evidence (`Own API key` / advertised-quote estimate vs. Provider-reported cost) **without** requiring customer tariffs, prepaid Niu balances, payment gateways or commercial qualification.
2. **Resale (`resale`, Niu Cloud / staging):** The platform operator qualifies commercial supply and publishes platform-wide customer selling prices (`/admin/pricing`). Customer organizations fund a shared prepaid balance (or use an installation-approved credit limit), and workspaces consume that shared capacity subject to workspace/key limits.
3. **End-user self-service BYOK (unimplemented boundary):** Downstream workspace users adding private upstream credentials in a multi-tenant resale deployment is a separate future capability. Do not infer end-user BYOK from administrator-managed preset connections.

## Goal-based user stories and observable outcomes

Each story is a realistic role-and-goal prompt, not a click script. For every story, inspect **entry preconditions**, **information available at the moment of decision**, **observable completion and state readback**, and **failure/permission/recovery branches** across desktop (`1440×900`), intermediate split-pane (`768px–1024px`, navigation open and closed), and mobile (`390×844`) viewports. Where an outcome requires an unsupported capability, record the limitation rather than treating it as shipped.

### 1. Public discovery, orientation and access lifecycle (`S01`–`S02a`)

| ID | Actor, precondition and goal | Information needed at decision time | Observable success and readback | Failure, edge and recovery branches |
| --- | --- | --- | --- | --- |
| **S01** | **Public visitor** arrives on Niu (`/` or `/models` or `/docs`) wanting to know whether Niu helps their coding agent discover, evaluate and manage models. | Clear statement of what Niu provides vs. what the agent and human own; whether models are available now; who pays (`Internal use` vs `Resale`); reachable `Models` and `Docs` navigation at desktop and mobile widths. | Visitor understands the agent feedback loop, sees real catalog models (or an honest empty catalog state with a role-appropriate next step), and reaches the two-document human entry (`Orientation` and `Build with Niu`) without internal jargon or broken `/help` dead ends. | Empty public catalog (`niu-287.4`) explains why no models are listed and offers a valid next step instead of assuming administrator authority; mobile (`390×844`) sign-in/public header retains access to `Models` and `Docs` (`niu-287.6`); `/help/*` resolves or redirects cleanly. |
| **S02** | **New or returning user** wants to sign in, register, or recover account access (`/login`). | Supported authentication methods (email/password, configured OAuth providers, or explicit access token where applicable), how a new user obtains an account, and how a forgotten password or expired token is recovered. | User authenticates, preserves their originally requested destination (`redirect` / `state.from`, including query and fragment), and lands in an authorized workspace or onboarding flow with custom deployment branding loaded before sign-in. | Invalid credentials, revoked sessions or rate-limited attempts show a plain-language remedy without echoing secrets; missing self-service registration or password reset (`niu-287.5`) states who can grant or reset access; unauthenticated `/v1/branding` does not fail with `401`. |

## Review coverage method and acceptance checklist

For each story (`S01`–`S23`), record in the review ledger:

1. **Role, operating mode & starting data:** Exact actor (`Visitor`, `Viewer`, `Workspace Admin`, `Org Owner`, `Coding Agent`, `Installation Operator`, `Provider Rep`), mode (`Internal use` vs `Resale`), and initial dataset (empty vs. populated vs. broken state).
2. **Observed path & decision evidence:** Whether the user/agent has the information required *at the moment of decision* (who pays, price/estimate vs. `Unknown`, scope of mutation, capability limits) without consulting source code or relaying internal IDs/JSON.
3. **Visual hierarchy & layout across viewports:**
   - Desktop (`1440×900` / `1280×720`): Full available management width between navigation and canvas padding (no fixed centered max-width except the `/generations` reading column), no duplicate `<h1>` headers, Subtle Manus-aligned surface tones without nested bordered card clutter.
   - Intermediate split-pane (`768px–1024px`, sidebar both open and collapsed) and Mobile (`390×844`): Zero horizontal document overflow, reachable top-level and section navigation (`AccountMenu`, `Models`, `Docs`), non-overlapping floating composers, and internal table scrolling.
4. **Component, keyboard & locale discipline:**
   - All choice controls use installed shadcn `DropdownMenu` primitives with right-aligned checkmarks (never native `<select>`, shadcn `Select`, or left radio dots); open states, alignment, `ArrowDown`/`Enter` selection, `Escape` dismissal, and trigger focus return verified in browser.
   - Secondary search outside `Models` and `Logs` uses a compact search icon + shadcn `Popover` preserving query state.
   - Both `en` and `zh-CN` inspected for untranslated strings, English initial-render flash, locale-formatted dates, and strict `Niu` / `Workspace` / `Provider` terminology.
5. **Branches & verification limits:** Explicit pass/fail/unverified status for empty, loading, error (`401`/`403`/`429`/`5xx`), permission denial, reload/revisit, and recovery states. A signed-in administrator or preconfigured staging dataset cannot establish a new user's or ordinary member's outcome. Read-only inspection cannot verify live mutations, paid inference or settlement; keep unexercised transitions marked `unverified` and linked to their Beads tasks.

The skill's [NN/g usability heuristics (recognition, system status, error recovery, real-world match)](https://www.nngroup.com/articles/ten-usability-heuristics/), [visual hierarchy principles](https://www.nngroup.com/articles/principles-visual-design/) and [WCAG 2.2 reflow/keyboard/focus standards](https://www.w3.org/TR/WCAG22/) govern this task model; they require rendered observation rather than source-only inference.
